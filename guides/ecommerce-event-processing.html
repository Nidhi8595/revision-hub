What I am building

I am building a small shopping data system. It runs on Databricks Free Edition. It uses small fake datasets.

Here is the story I test. A customer places an order. The payment succeeds. Later the parcel ships. Another customer cancels an order. Sometimes an event arrives twice. Sometimes it arrives late.

My system must handle these cases correctly. It must keep the original events. It must find bad data. It must not count the same event twice. It must show the right business results.

I create fake data with Python. I save it as JSON files. I process it with Databricks. I store the results in Delta tables.

From my project · Overview · Learning project

What I will learn#

Cost and scope#

I use Databricks Free Edition and small, fake datasets. I do not need Kafka, paid services, external databases or real customer data. I start with file-based processing. Then I test the incremental processing that the platform supports.

Added contextFree Edition

Free Edition gives me serverless compute only. Custom compute is not supported. This matters later, because serverless compute limits which streaming triggers I can use (see Step 7).

The big picture

My project has five stages. I also keep track of which events were processed. That helps me test new arrivals and safe restarts.

This layering follows the medallion architecture. It improves structure and quality step by step, from Bronze to Silver to Gold.

from datetime import datetime, timedelta, timezone
from pyspark.sql import Row
from pyspark.sql.types import *

PATH = "/Volumes/ecommerce/bronze/event_landing/input"
start = datetime(2026, 10, 27, 9, tzinfo=timezone.utc)
events = []

def add(id, typ, order, minute, amount=None, **extra):
    events.append({
        "event_id": id, "event_type": typ, "order_id": order,
        "event_time": (start + timedelta(minutes=minute)).isoformat(),
        "received_at": (start + timedelta(minutes=300)).isoformat(),
        "amount": amount, **extra
    })
  • Imports bring in tools for dates, times and Spark.
  • start sets the starting date and time for the fake events.
  • events = [] creates an empty list.
  • add() creates an event with its details and saves it in the list.

The loop creates 40 orders with different amounts, customers and products.

Python
# Generate 40 orders and their related events
for i in range(1, 41):
    order = f"ORD{i:03d}"
    amount = float([250, 500, 750, 1000, 1500][i % 5])
    product = f"PRD{(i % 8) + 1:03d}"

        customer_id=f"CUS{(i % 15) + 1:03d}")

        order, m + 1, amount / 2 if i % 7 == 0 else amount,
        payment_id=f"PAY{i:03d}")

        product_id=product, quantity=20)
    add(f"STK-OUT-{i:03d}", "INVENTORY_SOLD", order, m + 3,
        product_id=product, quantity=-1)

            shipment_id=f"SHP{i:03d}")

Step 3 · Save the events as JSON

From my project · Step 3 of 11 · Save as JSON files

My processing system needs input files. They act like new events arriving from a shopping application. I save the generated events as separate JSON files inside the Volume. Each batch represents events arriving at a different time. I keep the original files unchanged so I can repeat my tests.

Python
schema = StructType([
    StructField(c, DoubleType() if c == "amount" else
                   LongType() if c == "quantity" else StringType(), True)
    for c in columns
])

for e in events:
    for c in columns:
        e.setdefault(c, None)

# Save five separate batches
size = (len(events) + 4) // 5

for n in range(5):

        (spark.createDataFrame(batch, schema)
         .coalesce(1).write.mode("overwrite")

print("Total events:", len(events))

Step 4 · Bronze layer

From my project · Step 4 of 11 · Bronze layer

Bronze keeps a record of what arrived, even when some records are incorrect. I read all five batches from the Volume and preserve every incoming event, including duplicates and invalid records.

  • Read the JSON event files from the Volume.
  • Create a streaming Bronze table named events.
  • Keep the original event fields and add source_file to identify each source file.
  • Let the pipeline manage incremental file processing.

Step 5 · Silver layer

From my project · Step 5 of 11 · Silver layer

Incorrect data can produce incorrect reports. So Silver cleans and validates Bronze data while keeping Bronze unchanged. I quarantine invalid records instead of losing them. Then I can investigate bad events without touching the raw Bronze data.

Silver checks required fields, data types, event types, amounts and duplicate event IDs. It finds missing IDs, invalid amounts, unknown event types and repeated event IDs. It saves usable records to Silver and keeps rejected records separately with a reason. I also keep track of duplicates, so I do not silently lose all evidence that they arrived.

My first design: streaming tables#

My first Silver design used streaming tables. A classification table flags each event with a quarantine_reason. Two more tables split valid and quarantined events.

SQL
CREATE OR REFRESH STREAMING TABLE ecommerce.silver.silver_event_classification AS SELECT *,
    CASE
        WHEN event_id IS NULL OR TRIM(event_id) = ''
            THEN 'MISSING_EVENT_ID'
        WHEN event_type IS NULL OR TRIM(event_type) = ''
            THEN 'MISSING_EVENT_TYPE'
        WHEN order_id IS NULL OR TRIM(order_id) = ''
            THEN 'MISSING_ORDER_ID'
        WHEN event_type NOT IN (
            'ORDER_CREATED',
            'PAYMENT_COMPLETED',
            'PAYMENT_FAILED',
            'INVENTORY_RECEIVED',
            'INVENTORY_SOLD',
            'SHIPMENT_CREATED',
            'SHIPMENT_DELIVERED',
            'ORDER_CANCELLED'
        )
            THEN 'UNKNOWN_EVENT_TYPE'
        WHEN event_type = 'PAYMENT_COMPLETED'
             AND (amount IS NULL OR amount <= 0)
            THEN 'INVALID_PAYMENT_AMOUNT'
        ELSE NULL
    END AS quarantine_reason
FROM STREAM(ecommerce.bronze.events);

CREATE OR REFRESH STREAMING TABLE ecommerce.silver.valid_events AS
SELECT * EXCEPT (quarantine_reason) FROM STREAM(ecommerce.silver.silver_event_classification)
WHERE quarantine_reason IS NULL;

CREATE OR REFRESH STREAMING TABLE ecommerce.silver.quarantined_events AS
SELECT * FROM STREAM(ecommerce.silver.silver_event_classification)
WHERE quarantine_reason IS NOT NULL;

Original event500Normal payment event
Exact duplicate500Simulates a retried or re-delivered event

So the streaming design let all three rows into valid data. A streaming Silver design needs an explicit strategy for comparing newly arriving events with previously processed IDs. I cannot assume a simple streaming filter detects conflicts across batches.

My fix: a clear policy and materialized views#

I use the pipeline's supported incremental processing and stateful capabilities, with a clear policy.

CasePolicy
Exact retriesKeep one logical event.
Conflicting event IDsQuarantine the conflicting versions.
Late-arriving eventsPreserve event-time history and handle them by policy.
Invalid recordsQuarantine with a reason.

I rebuild Silver as materialized views. A materialized view lets me compare duplicates inside the newly arrived records and also against the existing records. That gives me deduplication overall.

silver_event_classification is the main table. It is a checklist for every event record:

  • event ID missing?
  • event type missing?
  • order ID missing?
  • event type supported?
  • does a completed payment have a positive amount?

If a rule fails, I record the reason. If no rule fails, validation_reason is NULL. That means the event passed these checks.

The statement is long, so I show it in four fragments, as they appear in my notes. The first fragment opens the view and the first rules.

Step A · Fingerprint each event#

SHA2 creates a fingerprint for an event. I build it from selected fields. TO_JSON turns a NAMED_STRUCT into text first.

SQL
SHA2(
    TO_JSON(NAMED_STRUCT(
        'event_type', event_type,
        'order_id', order_id,
        'customer_id', customer_id,
        'amount', amount,
        'event_time', event_time
    )),
    256
) AS payload_hash

The first two have the same fingerprint, because the selected fields match. The third differs, because its amount changed. An event ID alone cannot tell me whether two records contain the same information.

Step B · Count versions per event ID#

SQL
event_stats AS (
    SELECT
        event_id,
        COUNT(DISTINCT payload_hash) AS versions
    FROM classified
    WHERE event_id IS NOT NULL
      AND TRIM(event_id) <> ''
    GROUP BY event_id
)

This groups records by event ID and counts how many different fingerprints each ID has. If an event appears five times with identical content, it still has one distinct fingerprint. If its content changes, the count goes up.

Step C · Combine validation with conflict detection#

SQL
SELECT c.*,
    CASE
        WHEN c.event_id IS NULL OR TRIM(c.event_id) = ''
            THEN 'MISSING_EVENT_ID'
        WHEN s.versions > 1
            THEN 'CONFLICTING_EVENT_ID'
        WHEN c.validation_reason IS NOT NULL
            THEN c.validation_reason
        ELSE NULL
    END AS quarantine_reason
FROM classified c
LEFT JOIN event_stats s ON c.event_id = s.event_id;

If PAY-EVT-001 has amounts 500 and 9999, both versions get CONFLICTING_EVENT_ID. I quarantine both versions. I do not trust one of them.

Step D · Valid and quarantined views#

SQL
CREATE OR REFRESH MATERIALIZED VIEW ecommerce.silver.valid_events AS
SELECT * EXCEPT
(validation_reason, quarantine_reason, payload_hash)
FROM ecommerce.silver.silver_event_classification
WHERE quarantine_reason IS NULL
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY event_id ORDER BY event_time) = 1;
  • WHERE quarantine_reason IS NULL removes events that failed my checks.
  • PARTITION BY event_id groups events with the same ID.
  • ROW_NUMBER() gives each row a number inside its group.
  • QUALIFY ... = 1 keeps one row per event ID. QUALIFY filters the results of window functions.

So identical retries do not appear multiple times in my valid output.

SQL
CREATE OR REFRESH MATERIALIZED VIEW ecommerce.silver.quarantined_events AS
SELECT * FROM ecommerce.silver.silver_event_classification
WHERE quarantine_reason IS NOT NULL;

Now I can investigate invalid events without deleting or changing anything in Bronze. When the pipeline refreshes, Databricks updates the views. It may refresh supported queries incrementally or recompute them when necessary.

Try the Silver checklist

I type an event. The rules run in the same order as my CASE. The first rule that fails sets validation_reason. If none fails, the event passes.

Step 8 · Gold current order status

From my project · Step 8 of 11 · Build Gold current order status

Event history tells me everything that happened. A current-status table shows where each order stands now. I derive the latest status of each order from its event history. I do not modify Bronze or Silver. The table has one current record per order.

SQL
CREATE OR REFRESH MATERIALIZED VIEW ecommerce.gold.current_order_status AS
WITH ranked_events AS (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY order_id
            ORDER BY event_time DESC, event_id DESC
        ) AS event_rank
    FROM ecommerce.silver.valid_events
    WHERE order_id IS NOT NULL )
SELECT order_id,
    event_type AS latest_event_type,
    event_time AS latest_event_time,
    CASE
        WHEN event_type = 'ORDER_CANCELLED'
            THEN 'CANCELLED'
        WHEN event_type = 'SHIPMENT_DELIVERED'
            THEN 'DELIVERED'
        WHEN event_type = 'SHIPMENT_CREATED'
            THEN 'SHIPPED'
        WHEN event_type = 'PAYMENT_FAILED'
            THEN 'PAYMENT_FAILED'
        WHEN event_type = 'PAYMENT_COMPLETED'
            THEN 'PAID'
        WHEN event_type = 'ORDER_CREATED'
            THEN 'CREATED'
        ELSE 'IN_PROGRESS'
    END AS current_status
FROM ranked_events
WHERE event_rank = 1;
  • ROW_NUMBER() ranks each order's events from newest to oldest.
  • event_rank = 1 selects the latest event for each order.
  • CASE translates the latest event into a readable business status.
  • The Gold view keeps the latest event's type and timestamp for troubleshooting.

Why does Gold show "Full recompute"? The view uses ranking to pick the latest event for each order. My pipeline reports that it recomputed this view instead of refreshing it incrementally. That is expected for this implementation. It differs from the incremental refresh I saw for valid_events.

Key learnings

Layers and event design#

  • Raw ingestion and business logic serve different purposes. I keep Bronze focused on ingestion. Validation and business rules live in Silver and Gold.
  • An event is not an order. One order can produce several events. I keep the event history instead of only the latest state.
  • The latest event can decide the current state. I use ROW_NUMBER() with event timestamps to pick one latest event per order. Window functions help here.
  • A pipeline graph shows dependencies. I could see Bronze feed Silver and Silver feed Gold.

Quality and validation#

  • Duplicates and conflicts are different. A retry can repeat an event. The same event ID with different payloads is a conflict. Blindly keeping the first record can hide bad data.
  • Quarantine is a data-quality tool. I separate invalid records, so one bad event does not silently become valid business data.
  • Technical success is not correct business logic. My Gold mapping worked as written. I still had to question whether INVENTORY_SOLD should map to IN_PROGRESS.
  • Validation covers business correctness, not only row counts. I checked unique order IDs, null IDs, duplicates, Silver-to-Gold reconciliation and quarantine reasons.

Incremental processing#

  • Incremental processing handles newly arriving data without rebuilding everything from scratch.
  • Auto Loader with read_files() and STREAM ingests JSON files into Bronze.
  • New-file testing: I added a new JSON event in a separate batch folder and updated the existing pipeline. I did not regenerate the original data.
  • End-to-end check: the new event reached Bronze, Silver classification and Silver valid events.
  • Triggered execution: a pipeline in Triggered mode processes available data when I run an update. It does not need to run continuously.
  • Refresh behaviour differs. valid_events showed incremental refresh. silver_event_classification and current_order_status showed full recompute in the observed runs.
  • Why it differs: comparing event versions or ranking events per order can take more work than appending new records. silver_event_classification must check duplicates and validity across the whole dataset.
  • Idempotency: I repeated the pipeline update and verified that my test event appeared once in valid_events.
  • History versus current state: Silver preserves valid events. Gold derives the latest order status from that history.

Honest limits#

  • A working result is not a fully tested system. I verified that a new event reached Bronze and Silver, and that it appeared once in valid output after a repeat update. I did not simulate a pipeline failure and recovery.
  • Debugging is part of implementation. When Spark could not infer the type of a field that only held None, I defined the schema explicitly.

Revision prompts

I use these to test myself. Open one to see my answer.

Why does Bronze keep duplicate and invalid events?

Bronze is my record of what arrived. If I remove records there, I lose the evidence. I can investigate bad events later, because Bronze stays unchanged. Validation and cleanup happen in Silver.

What is the difference between a duplicate and a conflicting event?

A duplicate is a retry. The same event ID arrives again with the same content. A conflict is the same event ID with different content, like PAY-EVT-001 with 500 and 9999. I keep one logical copy of a retry. I quarantine every version of a conflict.

Why do I fingerprint events with SHA2?

An event ID alone cannot tell me whether two records hold the same information. I hash selected fields (event_type, order_id, customer_id, amount, event_time). Same content gives the same fingerprint. Then COUNT(DISTINCT payload_hash) per event ID tells me how many versions exist. More than one means a conflict.

Why did my first Silver design fail on PAY-EVT-001?

My streaming tables only classified each row on its own. A streaming Silver design needs an explicit strategy to compare new events with IDs it has already seen. I cannot assume a simple filter detects conflicts across batches. Silver as materialized views lets me compare within new records and against existing ones.

Which time does Gold use to find the latest event: event time or received time?

Event time. Gold ranks with ORDER BY event_time DESC, event_id DESC. So an old event that arrives late cannot replace a newer one. In my data every event has the same received_at, so it could not help anyway.

What is the difference between event history and current state?

History is every valid event of an order in time order. It lives in valid_events. Current state is one row per order with the status from its latest event. It lives in gold.current_order_status. An event is not an order. One order produces many events.

Why does Gold show "Full recompute" while valid_events is incremental?

Gold ranks events per order to pick the latest one. My pipeline reported a recompute for this view. That is expected here. The same goes for silver_event_classification, which checks duplicates and validity across the whole dataset. Refresh behaviour differs per table, so I inspect it.

What does Triggered pipeline mode do?

It processes the data that is available when I run an update, then stops. It does not need to run continuously. It is a finite run, not a permanent service.

Why are 26 orders IN_PROGRESS in Gold?

For most orders, the last event in time is INVENTORY_SOLD. My CASE sends every event type it does not list, including INVENTORY_SOLD, to the ELSE branch, which is IN_PROGRESS. The query works as written. The business rule is the open question.

What did I verify, and what did I not?

I verified that a new event reaches Bronze and Silver. I verified that it appears once in valid_events after a repeat update. I verified Gold has one row per order, and that Silver and Gold agree on 42 orders. I did not simulate a real pipeline failure and recovery. I did not run continuous streaming. I did not show sales totals.

Added context: how this connects to CDC, CDF and SCD

Added contextnot part of my project

This section comes from a separate reference note on incremental data engineering. My project did not build any of it. I include it to place my project on the map.

Imagine a customer table with 100 million rows. Yesterday only 5,000 customers changed. Do I really process all 100 million again? Sometimes yes. A full load can be simple, reliable and fine for small data, an initial copy, or a complete snapshot. When a large dataset changes all the time, repeated full loads create extra work. That is where incremental processing helps.

These terms are related, but they are not five versions of one technology. I answer five separate questions:

QuestionPossible answersWhere my project sits
How much data do I process?Full load or incremental loadIncremental: new JSON files, read_files + STREAM
How do I know what changed?Timestamp, increasing ID, cursor, arriving files, snapshot comparison, or a CDC feedArriving files in the Volume
Where did the change come from?A source system or a lakehouse tableFiles from a (fake) shopping app
How do I apply the change?MERGE, AUTO CDC, or other logicMaterialized views and streaming tables. No MERGE, no AUTO CDC
How should the target show history?Current state, SCD Type 1, SCD Type 2Silver keeps event history. Gold keeps current state. No SCD built

Once a change is already inside the lakehouse, Change Data Feed (CDF) can expose row-level changes of a Delta table to downstream processing. CDF answers a different question from source-side CDC. AUTO CDC is a streaming flow in Lakeflow Spark Declarative Pipelines. It is a stretch topic for me, next to the Change Data Feed goal above.
