1Overview

Source §1 · pp. 1–6

The core question

Overview · pp. 1–2

The architecture problem is rarely "Where should I put my data?"

It starts with a harder question: What does my data platform actually need to do?

A platform may need to support:

  • SQL reporting
  • raw and semi-structured data
  • data science and AI
  • data spread across clouds or business domains

That leads to bigger questions. How is the data stored? Who owns it? How is it governed? How can teams use it without unnecessary copies?

A warehouse, lake, lakehouse, data mesh and data fabric are not competing versions of the same architecture. Each one focuses on a different problem.

  • Data warehouse: structured analytical data.
  • Data lake: flexible and scalable data storage.
  • Data lakehouse: lake-oriented storage with stronger table and analytical capabilities.
  • Data mesh: decentralized data ownership across business domains.
  • Data fabric: connecting, discovering and governing data across distributed environments.

They can work together. A lakehouse can be the technical foundation for a data mesh. A data fabric can connect data across warehouses, lakes and lakehouses. A warehouse can keep serving a specialized analytical workload next to a lakehouse. Modern cloud platforms also blur the old capability boundaries.

The point I keep

This is not about finding one architecture that replaces all the others. It is about knowing which problem each pattern is designed to address.

1.1 Think in problems, not labels

§1.1 · pp. 3–5

Instead of asking "Should we use a warehouse, lakehouse, mesh or fabric?" I start with "What problem are we actually trying to solve?"

If the problem is mainly about… I investigate…
Structured analytical processing Warehouse
Flexible, scalable data storage Data Lake
Shared analytical foundation across workloads Lakehouse
Decentralized data ownership Data Mesh
Connecting distributed data environments Data Fabric
Several of these problems together A combination of patterns

Source caveat

This table is deliberately a starting point, not a decision table. The real architecture depends on workload, governance, organizational structure, existing investments and operational constraints.

I made a small picker from this table. I tick the problems I have and it shows what to investigate.

1.2 Five concepts. Five different architectural questions.

§1.2 · p. 5
Concept The question it primarily answers
Data Warehouse How do we reliably store and process structured data for analytics?
Data Lake How do we store large volumes of different types of data with flexibility?
Data Lakehouse How do we combine flexible lake storage with reliable analytical data management?
Data Mesh How do we organize data ownership across business domains?
Data Fabric How do we connect, discover, govern, and access data across distributed environments?

1.3 A small reality check

§1.3 · pp. 5–6

Modern platforms do not always fit neatly into these categories. Cloud platforms increasingly combine capabilities that used to belong to different architectures.

The source gives two examples. Microsoft Fabric supports both warehouse and lakehouse approaches over a common data foundation. AWS describes architectures that combine data lakes, warehouses and other purpose-built data stores.

So "a warehouse does X while a lake does Y" helps me learn the foundations. It does not describe every modern platform. The categories still matter. Their boundaries are becoming more porous.

Added context · checked 8 Nov 2026

Microsoft's decision guide for Fabric says both the Warehouse and the Lakehouse store data in Delta Lake format in OneLake. It also lists where they differ: Spark versus T-SQL development, multi-table transactions, and data types.

AWS's modern data architecture guide talks about connecting data lakes, data warehouses, operational databases and purpose-built services into one coherent whole.

2Why modern data architecture became complicated

Source §2 · pp. 7–13

2.1 The data problem kept changing

§2.1 · pp. 7–8

Nobody decided one day that they needed five architectures. The patterns appeared because the problems around data kept changing.

Traditional analytical systems worked well for structured reporting. Then organizations collected more data, in more formats, for more kinds of work: logs, events, semi-structured data, historical records, streaming data, machine learning inputs, and data spread across systems.

The challenge also became organizational. More teams needed to produce, use, govern and share data.

So the story is not a straight line:

Warehouse → Lake → Lakehouse → Mesh → Fabric

It is a loop:

2.2 The pressure was coming from everywhere

§2.2 · pp. 8–10

Several changes happened together.

  • More data. Much larger amounts of historical and operational data. Storage could no longer be designed around a small, predictable set of datasets.
  • More types of data. Logs, events, JSON, documents, media and other semi-structured or unstructured data joined the workflows.
  • More workloads. BI stayed important. Data engineering, data science, machine learning and AI added new ways to use the same data.
  • More real-time data. Some use cases could not rely only on scheduled batch processing. Streaming added requirements.
  • More distributed environments. Data sits in operational databases, SaaS applications, cloud platforms, regions and business systems. One physical location was not always practical.
  • More governance. Security, access control, lineage, privacy, data quality and regulation became part of the architecture.
  • More teams. This raised a new question: can one central data team keep managing every data decision as the organization grows?

That last point is where the problem became bigger than storage and processing.

2.3 The architecture question changes

§2.3 · pp. 10–11

At first the question was: How do we store and process data efficiently?

Over time I also had to ask:

  • How do we make data reliable?
  • How do we govern and discover it?
  • How do we connect data across different environments?
  • How do we let different teams work with data without unnecessary complexity?

These are related, but they are not the same problem.

  • Warehouse, lake and lakehouse mainly describe technical approaches to storing and processing data.
  • Data mesh adds an organizational view: ownership and responsibility across business domains.
  • Data fabric focuses on connecting, discovering and governing data across distributed environments.

Modern data architecture is not only about where data is stored. It is also about how data is managed and who is responsible for it.

2.4 Architecture became more than infrastructure

§2.4 · pp. 11–13

I can look at an architecture from three connected perspectives.

Technical

  • Where is data stored?
  • How is it processed?
  • How are analytical tables managed?
  • Which workloads need to run on it?

Data management

  • How is data discovered?
  • Who can access it?
  • How is lineage tracked?
  • How is it governed?

Organizational

  • Who owns the data?
  • Who is responsible for its quality?
  • How much independence should business domains have?
  • How much responsibility should stay with a central data team?

These perspectives overlap but they are not interchangeable. That is why two organizations can use similar technology and still make different architectural choices.

Question to carry forward

Instead of asking which architecture is the latest, I ask: What responsibility is this architectural pattern designed to address?

3Understanding the architecture landscape

Source §3 · pp. 14–20

3.1 Five names, different questions

§3.1 · p. 14

The five terms can look like five competing choices. They are not describing the same thing.

  • Warehouse, lake and lakehouse mainly describe how data is stored and processed.
  • Data mesh focuses on ownership, domain responsibility, data products and federated governance.
  • Data fabric focuses on connecting, discovering, integrating and governing data across distributed environments.

So I first ask what problem each one is trying to solve, not which is better.

3.2 Three main architectural dimensions

§3.2 · pp. 14–16
Dimension Question Where it fits
Technical architecture Where does the data live, and how do I process it? Warehouses, lakes, lakehouses. They differ in storage, schemas, processing, transactions and analytical capabilities.
Integration and access How do we discover, connect, govern and access data across environments? Data fabric, conceptually. It can use metadata, integration, federation, virtualization and discovery.
Organizational model Who owns the data, and who produces and maintains it? Data mesh: domain ownership, data as a product, self-service capabilities, federated governance.

Mesh is therefore not simply another storage technology.

Once I separate these responsibilities, the landscape is easier to reason about. A lakehouse can provide a technical foundation. A data fabric can connect that environment with other distributed systems. A data mesh can define how business domains own and manage data. They coexist instead of competing for the same position.

3.3 The same environment can contain different architectures

§3.3 · pp. 16–17

I do not have to choose one architecture for the whole environment. An organization could have:

  • a warehouse supporting established BI workloads,
  • a data lake storing diverse raw data,
  • a lakehouse as a shared analytical foundation,
  • fabric capabilities connecting data across other environments,
  • mesh principles defining ownership across business domains.

These can be different responsibilities within one broader architecture.

3.4 Architecture is not the same as a product

§3.4 · pp. 18–19

An architecture boundary is not always a product boundary.

  • A warehouse can be a complete analytical environment or one component of a larger platform.
  • A data lake can be the storage foundation while different processing engines work on top.
  • A lakehouse can combine storage, table management and processing and still be part of a wider environment.
  • Data mesh and data fabric are even less tied to one technology. They can span platforms and environments.

So two diagrams can look very different and use the same words. A single platform can offer capabilities from several categories. A larger architecture can combine several platforms.

Patterns are lenses, not boxes

The names are useful as architectural lenses. I should not treat them as perfectly isolated boxes. I also should not treat a vendor product as the same thing as a pattern.

3.5 A better mental model

§3.5 · pp. 18–19

Three separate questions:

  1. Where and how is data stored and processed? → Warehouse, Data Lake, Lakehouse
  2. How is distributed data connected and accessed? → Data Fabric
  3. How is data ownership organized? → Data Mesh

Solving one does not automatically solve the others.

  • A lakehouse gives a strong technical foundation. It does not decide which business domain owns the data.
  • A fabric helps connect and discover distributed data. It does not decide who is responsible for its quality.

Architecture is a set of decisions

Architecture is not one decision. It is a set of related decisions about storage, processing, integration, governance and ownership.

3.6 The landscape is becoming composable

§3.6 · pp. 19–20

A modern environment can combine patterns, each for a different need. For example: a lakehouse as the main analytical foundation, a warehouse for specific workloads, fabric capabilities to connect distributed data, and mesh principles for domain ownership.

This does not mean every organization needs every pattern. I choose architectural ideas for the problems they solve, not because they are newer or popular elsewhere.

Why this matters for me as an engineer. I stop asking "Which architecture should we adopt?" I ask "Which responsibilities does our data environment need to satisfy?" Then I evaluate the technical foundation, integration needs, governance, ownership model, existing investments and operational constraints. The architecture emerges from the problems.

4From warehouse to lakehouse

Source §4 · pp. 21–29

4.1 Why warehouses emerged

§4.1 · pp. 21–22

The early problem was simple: How can we run analytics without affecting the systems that run the business?

Operational systems handle transactions: orders, payments, customer updates, inventory. Analytical workloads scan large amounts of historical data, join datasets, calculate aggregates and support reporting. Running both on one system creates competing demands.

The warehouse separated them:

Operational systems → Data movement → Analytical warehouse → BI / Reporting

Why structure mattered. Traditional warehouses focused on structured, relational data and predefined schemas. That made business data easier to organize and gave predictable access for reporting and BI.

The trade-off: data generally had to be understood and structured before it entered the analytical model. That worked for structured business data. Then a new question appeared: How can we store data that does not fit easily into a traditional warehouse?

4.2 Why data lakes emerged

§4.2 · pp. 22–23

Organizations now had logs, events, files, semi-structured data, machine-generated data and large historical datasets. The question became: How can we store large amounts of diverse data without structuring everything first?

A data lake typically uses scalable storage and keeps data in different formats. I do not force every dataset into a predefined schema at once. I store it flexibly and structure it when a workload needs it. This is commonly associated with schema-on-read.

Multiple data sources → Scalable storage → Different processing engines → Different analytical workloads

This helped data engineering, data science and machine learning.

But flexibility was not the whole problem. Storage alone does not automatically give reliable tables, transactions, governance, data quality or a strong analytical experience. The next question: Can we keep the lake's flexibility and add the reliability and analytical capabilities of a mature data platform? That sets up the lakehouse.

4.3 What the lakehouse was trying to change

§4.3 · pp. 23–25

The goal was not to make warehouses obsolete. Many organizations used both lakes and warehouses for different workloads:

Data lake → ETL / data movement → Warehouse

The lake supported flexible workloads. The warehouse served curated BI data. This worked, but it could mean more pipelines, duplicated data, synchronization work and governance across separate environments.

The lakehouse response: bring stronger data management and analytical capabilities to a lake-oriented storage foundation.

Scalable storage + reliable table management + analytical processing

Modern lakehouse capabilities can include:

  • ACID transactions
  • schema enforcement and evolution
  • metadata and table management
  • versioning
  • governance
  • SQL and BI access
  • support for data engineering, streaming, ML and AI workloads

A lakehouse is more than flexible storage. It aims to make that storage a reliable analytical foundation for multiple workloads.

The architectural question: What capabilities do I need to turn flexible storage into a reliable analytical data foundation? This is what separates the lakehouse discussion from the data lake discussion.

4.4 The technical capabilities behind the lakehouse

§4.4 · pp. 25–27

I understand the lakehouse better through capabilities than through the name.

  • Open table formats. A table format is a structured layer over files in object storage. It defines how tables and metadata are represented. It helps processing engines work with the data more reliably.
  • ACID transactions. Stronger consistency when several operations change or read data.
  • Schema enforcement and evolution. Control incoming data, but let schemas change as requirements change.
  • Versioning and metadata. Track table state and history, support reproducibility, make data management more predictable.
  • Governance. With more teams on one foundation, access control, discovery, lineage and similar capabilities matter more.

These capabilities belong to the broader platform around the storage layer. They are not simply features of object storage.

The architectural shift

A lakehouse is not just object storage + SQL. A better view is: flexible storage + table management + reliability + governance + processing. Implementations differ across platforms. The goal is similar: make flexible storage a dependable foundation for multiple workloads.

Added context · checked 8 Nov 2026

The three table formats the source names have official documentation. Delta Lake documents ACID transactions, schema enforcement and time travel. Apache Iceberg describes an open table format that lets several engines work safely on the same tables. Apache Hudi adds transactions and efficient updates and deletes to data lakes. Databricks explains the lakehouse idea in What is a data lakehouse?

4.5 Why the warehouse still matters

§4.5 · pp. 27–28

Warehouses still make sense for workloads that depend on structured data, SQL analytics, governed access and established BI workflows. Modern warehouse platforms have also evolved, so the old boundary with the lake is less strict.

The question is not "Warehouse or lakehouse?" It is: Which workloads and requirements does each part of the environment need to support?

An organization may keep a warehouse for established BI and use a lakehouse for data engineering, machine learning, streaming or more diverse data. So I do not read this as a simple replacement chain.

4.6 The evolution was about capabilities, not replacement

§4.6 · p. 28
Architectural response Main pressure
Data Warehouse Separate analytical workloads from transactional systems and support structured analytics
Data Lake Store large and diverse datasets with greater flexibility
Data Lakehouse Add stronger table management and analytical capabilities to lake-oriented storage

The history explains why each pattern emerged. It does not mean a newer one makes the older one obsolete.

New requirement → existing architectural limitation → additional capability → broader architectural model

4.7 The question changes again

§4.7 · pp. 28–29

Warehouse, lake and lakehouse are about the technical foundation. Then another problem appeared: What happens when data is distributed across teams, business domains, platforms and locations?

A capable platform is only part of the answer.

  • Ownership. A central team may manage data from many business areas. As domains and consumers grow, the people closest to the data may need more ownership over how it is produced, maintained, documented and shared. The question moves from "Where should we store and process the data?" to "Who should own and manage the data?" That is what data mesh tries to address.
  • Distribution. Useful data stays spread across warehouses, lakes, operational systems and cloud platforms. I still need to discover, connect, govern and access it. The question: How can we work with distributed data without putting everything into one physical environment? That is where data fabric enters.

Data Mesh → organizational ownership and responsibility. Data Fabric → distributed integration, discovery, access and governance.

Neither is simply the next storage technology after the lakehouse. They address a different dimension.

5Data mesh and data fabric

Source §5 · pp. 30–39

The problem is no longer only storing and processing data. The questions are now: Who owns the data? How is it managed? How can people discover it? How can teams work with data that stays distributed?

5.1 Data mesh

§5.1 · pp. 31–32

Data mesh mainly focuses on the organizational side of data. The commonly discussed principles:

  • Domain ownership. Business domains take responsibility for the data they produce.
  • Data as a product. Data has clear ownership, quality expectations, documentation and consumers.
  • Self-service data infrastructure. Shared capabilities let teams work with data without waiting on a central team for every task.
  • Federated governance. Common rules are coordinated across domains instead of being fully centralized.

These principles describe how responsibility is organized. A lakehouse can provide technology that supports a data mesh. Adopting a lakehouse does not create one.

Added context · checked 8 Nov 2026

The source lists Martin Fowler's site as its data mesh reference. The article, Data Mesh Principles and Logical Architecture, is by Zhamak Dehghani (3 Dec 2020). Her wording of the four principles is slightly longer: domain-oriented decentralized data ownership and architecture, data as a product, self-serve data infrastructure as a platform, and federated computational governance. The source shortens the last two. See the accuracy note at the end.

5.2 Data mesh starts with ownership

§5.2 · pp. 31–32

Take an organization where teams produce different data:

  • Sales understands customers and opportunities.
  • Finance understands financial transactions.
  • Operations understands operational events.
  • Marketing understands campaigns and engagement.

A central data team can manage all of it, but it may lack the domain knowledge of the teams that produce it. As the organization grows, this becomes a bottleneck.

The question: Can the teams closest to the data take more responsibility for producing and maintaining it? That is domain ownership.

5.3 Data as a product

§5.3 · p. 32

If a domain is responsible for data that other teams use, people must be able to depend on it. I think about:

  • Quality
  • Documentation
  • Discoverability
  • Ownership
  • Accessibility
  • Intended consumers

The goal is not just to make a dataset available. The goal is to make it usable and trustworthy for the people who depend on it.

5.4 Self-service does not mean every team builds everything alone

§5.4 · pp. 33–34

If every domain owns its data, I do not want every team to build its own storage, pipelines, security, monitoring and deployment. That swaps one central bottleneck for many duplicated efforts.

So a shared platform provides capabilities such as:

  • storage and processing
  • pipelines and orchestration
  • access control
  • monitoring
  • metadata and discovery
  • data quality
  • deployment and operational workflows

That is why data mesh is better understood as a sociotechnical model, not another storage architecture.

5.5 Federated governance

§5.5 · pp. 34–36

Once domains own data and shared infrastructure enables self-service, a new question appears: How do we stop every domain from following completely different rules?

A mesh does not mean each domain sets its own rules without coordination. I still need common expectations for:

  • security
  • access
  • privacy
  • compliance
  • interoperability
  • data quality
  • metadata
  • organizational policies

The aim is common standards without moving all responsibility back to one central team.

Domain ownership + Self-service platform + Federated governance

5.6 Where data fabric fits

§5.6 · pp. 36–38

Mesh asks "Who should own and manage the data?" Fabric starts elsewhere: How can we work with data spread across many systems and environments?

Data may sit in operational databases, warehouses, lakes, SaaS applications, cloud platforms and other systems. Moving everything into one physical location may not be practical or necessary.

A data fabric focuses on making distributed data discoverable, connected, integrated, governed and accessible. A fabric approach can involve:

  • metadata and discovery
  • data integration
  • federation or virtualization
  • semantic or contextual layers
  • automation
  • governance

Fabric is broader than querying data where it already lives. It can use different mechanisms to make distributed data easier to understand and use.

5.7 Data mesh vs data fabric

§5.7 · pp. 38–39
Data Mesh Data Fabric
Primary question Who owns and manages the data? How can distributed data be connected and accessed?
Main focus Domain ownership and data products Integration, discovery, access and governance
Nature Organizational / sociotechnical model Distributed data integration and access approach
Technology dependency Can use different technical platforms Can span multiple data environments
Can coexist? Yes Yes

Mesh organizes responsibility. Fabric organizes access across distributed data.

They can exist together. A domain stays responsible for its data product under mesh principles. Fabric capabilities help other teams discover and access that data across environments.

Source caveat

A technical platform can support these approaches. Adopting a platform does not automatically create a data mesh or a data fabric. The architecture still needs ownership, governance and operating practices.

6The architecture layer model

Source §6 · pp. 40–42

6.1 Different questions, different responsibilities

§6.1 · pp. 40–41

Four questions connect the patterns:

Question What I am thinking about
Where does my data live? Storage
How is it processed and managed? Processing
How do we work with data across systems? Integration and access
Who owns and governs the data? Ownership and governance
  • Data warehouse: structured analytical storage and processing
  • Data lake: flexible and scalable data storage
  • Lakehouse: flexible storage with stronger table management and analytical processing
  • Data fabric: connecting and working with distributed data
  • Data mesh: organizing ownership, data products and governance across domains

These are different responsibilities, so they can exist together. They are different parts of the same architecture, not five answers to one problem.

6.2 A mental model, not a fixed stack

§6.2 · p. 41

I should not read the concepts as a strict technical stack. A real architecture might use a lakehouse as the main data platform, fabric capabilities to connect distributed data, and mesh principles for domain ownership.

The order does not matter. What matters is which problem each one solves. So I ask "Which problems does our architecture need to solve?" and not "Which architecture should we use?"

6.3 The same architecture can use different ideas

§6.3 · p. 42

An organization might have a lakehouse as the main analytical foundation, a warehouse for specific BI workloads, fabric capabilities to connect systems, and mesh principles for domain ownership.

That is not inconsistent. Different parts solve different problems.

6.4 A simple way to read the model

§6.4 · p. 42

I start with the question, not the architecture name.

  • Where and how is data stored and processed? → Technical foundation
  • How is distributed data connected and accessed? → Integration and access
  • Who owns and manages the data? → Organizational model

Rule

Start with the problem. Then look at the architecture.

7Comparing the architectures

Source §7 · pp. 43–45

7.1 Compare them by responsibility

§7.1 · p. 43

Questions I use when comparing:

  • What is each mainly designed to do?
  • What kind of data does it handle?
  • Where is the data stored?
  • How is it processed?
  • How is it governed?
  • Who is responsible for it?
  • What does the engineering team need to operate?

These are not all the same type of architecture. Warehouse, lake and lakehouse are mainly technical approaches. Mesh focuses on ownership. Fabric focuses on working with distributed data. So I compare the responsibility each one addresses and I do not treat all five as competing technologies.

7.3 The comparison has limits

§7.3 · p. 45

This table shows the traditional differences. It is not a strict checklist. Modern platforms combine capabilities once tied to different architectures.

  • Warehouses can work with external and non-traditional data.
  • Data lakes can gain stronger table and transaction capabilities through modern table formats.
  • Lakehouses can provide SQL and BI experiences similar to warehouses.
  • Data fabric can work with data that stays physically distributed.
  • Data mesh can use different underlying technologies.

What stays different

Capabilities may overlap, but the problems these patterns were designed to solve are still different.

8These architectures can coexist

Source §8 · pp. 46–53

8.1 Lakehouse + warehouse

§8.1 · pp. 46–48

A lakehouse does not mean the warehouse has to go. Many teams already run important BI and reporting on a warehouse, and moving it all at once may not make sense. The team can keep the warehouse and add a lakehouse for other needs:

  • The lakehouse handles raw data, data engineering, streaming and ML/AI.
  • The warehouse handles structured SQL models and BI reporting.
  • Data can move between them when needed.

The key question is not "Which one should we keep?" It is "Which workload should use which system?"

There is another option. Some platforms run warehouse workloads directly on lakehouse data. Databricks, for example, provides data warehousing through Databricks SQL and SQL warehouses on its lakehouse. This can reduce the need for separate copies of data. So "warehouse + lakehouse" does not always mean two separate systems. It depends on the platform and the workload.

Engineering insight (from the source)

A highly managed platform does not make architectural decisions disappear. It moves those decisions from infrastructure configuration toward workload, data, capacity, governance and application design.

8.2 Lakehouse + data mesh

§8.2 · pp. 48–49

A lakehouse solves a technical problem. Data mesh is about who owns the data and how teams work with it. So they work together.

With a mesh approach each team takes responsibility for its data as a data product. The lakehouse is the shared technical foundation underneath.

Business domains → Own their data → Lakehouse → Shared governance and access

For example, Sales manages a sales data product. Finance manages finance data. Both use the same lakehouse platform and ownership stays in the domains.

  • Lakehouse answers: "How do we store and process the data?"
  • Data mesh answers: "Who owns and manages the data?"

Using a lakehouse does not automatically create a data mesh. I still need domain ownership, clear responsibilities, data products and suitable governance.

8.3 Lakehouse + data fabric

§8.3 · pp. 49–50

The lakehouse is a place to store, manage and process data. The fabric helps connect and manage data across different systems. This helps when data is spread across many places, for example:

CRM + ERP + SaaS + Lakehouse + Warehouse

The fabric approach helps the team discover this data, connect it, apply governance and make it easier to access. The lakehouse becomes one of the main data platforms in that environment.

  • Lakehouse: store and process data
  • Data fabric: connect, discover, govern and provide access across data sources

The fabric does not have to mean moving all data into the lakehouse. Some data stays in its original system. Depending on tools and design, the organization may use integration, federation or virtualization. That helps when data is already spread across platforms and replacing them is not practical.

8.4 Warehouse + data fabric

§8.4 · pp. 50–52

CRM + ERP + SaaS + Warehouse

The warehouse keeps serving BI and reporting. The fabric connects the warehouse with other sources and helps with finding data, connecting systems, applying governance and making data easier to access.

The warehouse still does its main job: analytical processing and reporting. The fabric works across the wider data environment. They solve different problems.

8.5 Lake + specialized processing

§8.5 · pp. 52–53

A data lake can work with separate processing systems. One platform does not need to handle every workload. The team keeps data in the lake and uses different tools for different jobs:

  • Spark for large-scale data processing
  • Streaming engines for real-time data
  • ML tools for model training
  • SQL engines for analytics

More tools can mean more configuration, monitoring, security work, data movement and operational overhead. So I look at the actual workloads before adding processing systems.

This is the main picture for how the patterns coexist. It draws the source's examples together: domains own data, a lakehouse is the technical foundation, and a fabric connects distributed platforms.

9Trade-offs

Source §9 · pp. 54–57

For each pattern I note what it gives me, what it costs, and when it may or may not fit.

§9.1 · p. 54

9.1 Warehouse

A warehouse gives me a structured place for analytical data. It works well when the main need is SQL analytics, reporting and BI. It can be less convenient for many data types or very flexible processing.

  • Engineering cost: Data often needs cleaning and modeling before it is ready for analysis.
  • Operational consideration: I manage models, workloads, access and performance.
  • When it may fit: structured analytics and BI are the main workloads.
  • When it may not fit: the platform must also handle very diverse data, large-scale engineering, streaming or ML in the same environment.
§9.2 · pp. 54–55

9.2 Data lake

A data lake gives me a flexible place for large amounts of structured, semi-structured and unstructured data.

  • Engineering strength: I can store data without fully modeling it first.
  • Engineering cost: I must manage data quality, structure, metadata and governance carefully.
  • Operational consideration: without good controls, the lake can become hard to understand and use.
  • When it may fit: flexible storage for many data types and different processing tools.
  • When it may not fit: the main need is ready-to-use BI and tightly managed analytical models.

Key trade-off

More storage flexibility also means more responsibility for managing the data.

§9.3 · p. 55

9.3 Lakehouse

A lakehouse brings storage, tables and processing together. That can reduce the number of separate systems for different data workloads.

  • Engineering strength: the same platform can support data engineering, SQL, BI, streaming and ML.
  • Engineering cost: I still design tables, pipelines, governance and workload management properly.
  • Operational consideration: one platform can support many workloads, but the workloads still have different needs.
  • When it may fit: I want one broader platform for several types of work.
  • When it may not fit: existing systems already meet the workloads well and there is little reason to change.

Key trade-off

A lakehouse can bring workloads together, but it does not remove the need for good engineering.

§9.4 · pp. 55–56

9.4 Data mesh

Data mesh shifts the focus from technology to ownership. Business domains, not one central team, take responsibility for their data products.

  • Engineering strength: teams closer to the data understand and manage it better.
  • Engineering cost: domain teams need the skills and time to manage data properly.
  • Operational consideration: I need clear ownership, shared standards and governance across teams.
  • When it may fit: many business domains produce and use important data and central ownership is getting hard to scale.
  • When it may not fit: the organization is small, has simple data needs, or lacks enough domain ownership to support the model.

Key trade-off

Data mesh changes who owns the data. It does not replace the underlying data platform.

§9.5 · pp. 56–57

9.5 Data fabric

Data fabric connects data across different systems. It can help teams find, access, integrate and govern data without forcing everything into one place.

  • Engineering strength: it can work across a mixed data environment.
  • Engineering cost: connecting many systems can become complex.
  • Operational consideration: I need consistent metadata, access rules, governance and integration processes.
  • When it may fit: data is spread across many existing systems that need to work together.
  • When it may not fit: the environment is small and simple enough that direct connections are easy to manage.

Key trade-off

Data fabric helps connect a distributed data environment. It does not have to become the place where all data is stored.

10How to choose an architecture

Source §10 · pp. 58–64

There is no single architecture that fits every organization. I start with the workloads, not the platform name. Open each step below. I work through them as a checklist and I tick the boxes only to track my own progress.

10.1 Start with the workload
§10.1 · pp. 58–59

What does the system actually need to do?

  • Is most of the work BI and SQL analytics?
  • Does the team handle large amounts of raw or varied data?
  • Is streaming important?
  • Does the team need ML or AI workloads?
  • Is data spread across many systems?
  • Do different business teams need to own their data?

A company with mostly BI workloads has very different needs from one handling real-time events, ML workloads and data from many business domains. Start with the problem. Then choose the architecture.

10.2 Look at the data
§10.2 · pp. 59–60
  • Data types: structured, semi-structured or unstructured
  • Data volume: how much data
  • Data speed: batch or continuous
  • Data location: one system or many
  • Data changes: how often it changes
  • Data sensitivity: security or regulatory requirements

A system that stores structured business data has different needs from one that collects millions of events a day. I also check where the data already lives. Moving everything into a new platform may not be necessary. Sometimes connecting to existing systems is enough.

10.3 Look at the workload
§10.3 · pp. 60–61
  • BI and reporting: how many users and queries run at the same time?
  • Data engineering: how much transformation and processing?
  • Streaming: must data be processed as it arrives?
  • ML / AI: feature engineering, model training or AI workloads?
  • Ad hoc analysis: do users need to explore data freely?
  • Data serving: does another application need data from the platform?

A platform built for dashboards differs from one that also handles streaming and ML. The goal is not one system that does everything. The goal is to understand the workloads the architecture must support.

10.4 Check the organization
§10.4 · pp. 60–61
  • Who owns the data?
  • Who manages the platform?
  • How many teams use the data?
  • Do teams work independently?
  • Is there a central data team?
  • How mature are the team's data practices?

This matters most for data mesh. A mesh needs clear domain ownership. If teams are not ready to own and manage their data, a mesh model may create more work than it solves. The same applies to governance: a larger, distributed environment usually needs clearer rules for access, quality, ownership and security.

10.5 Check the existing setup
§10.5 · pp. 61–62
  • What platforms are already in use?
  • What data is already stored there?
  • Which pipelines already exist?
  • What tools does the team know?
  • What would need to change?
  • Can the new architecture work with the existing systems?

A new architecture does not mean starting from zero. A team with a warehouse that works well for BI may add a lakehouse for other workloads instead of moving everything. Existing technology, skills and integrations all affect the final design.

10.6 Check governance and compliance
§10.6 · p. 62
  • Who can access the data?
  • Is the data sensitive?
  • Are there regulatory requirements?
  • Do we need data lineage?
  • How will data quality be checked?
  • Where can the data be stored?

A company may have data in different regions and need different access rules for different teams. So governance is part of the design from the start, not something added later.

10.7 Check cost and platform dependencies
§10.7 · pp. 62–63

I do not look only at the platform price.

  • Storage costs
  • Compute costs
  • Data transfer
  • Licensing
  • Operations and maintenance
  • Skills and training
  • Dependence on specific platforms or tools

Two architectures can have very different cost patterns. One may need more data movement. Another may need more compute. An existing platform may be cheaper to keep than to replace. I estimate the full cost of running the architecture, not just the platform price.

10.8 Put the requirements together
§10.8 · pp. 63–64

I now have things to check: data, workloads, BI needs, streaming, ML / AI, governance, team structure, existing systems, cost and platform dependencies. Putting them together does not give an automatic answer. It gives a clearer picture of what the architecture needs to support. For example:

Requirement What we may need
Large and varied data Flexible data platform
Heavy BI Strong SQL and BI support
Streaming Streaming capabilities
ML / AI ML and AI support
Many business domains Clear data ownership
Data across many systems Integration and access capabilities
Strict governance Strong security and governance

The same organization may need more than one pattern. Architecture selection is usually a requirements exercise, not a simple product choice.

11Common misconceptions

Source §11 · pp. 65–68

Each card starts with the myth. I open it to see the correction.

Myth11.1 “A lakehouse replaces every warehouse”
§11.1 · p. 65

Reality

  • A lakehouse can support many warehouse-style workloads.
  • That does not mean every warehouse should be removed.
  • A company may keep an existing warehouse while using a lakehouse for other workloads. Some platforms also provide warehouse capabilities directly on lakehouse data.

Why it matters: the choice depends on workloads, existing systems and requirements.

Myth11.2 “Data lakes are obsolete”
§11.2 · p. 65

Reality

  • A data lake is still useful.
  • It stores large amounts of different data types and works with many processing tools.
  • Modern data lakes can use table formats and other features that add transactions, schema management and better data management.

Why it matters: a lake is still a valid part of a modern architecture. The right question is what the system needs, not whether the technology is old or new.

Myth11.3 “Data mesh is a product”
§11.3 · p. 65

Reality

Data mesh is not a single software product. It is an organizational and architectural approach to data ownership. It covers domain ownership, data products, self-service data infrastructure and shared governance. Different tools can support these ideas.

Why it matters: buying a tool does not create a data mesh. The organization also needs the right ownership and ways of working.

Myth11.4 “Data fabric means one centralized data store”
§11.4 · pp. 66

Reality

  • Data fabric does not mean putting all data in one place.
  • It is about connecting and managing data across systems.
  • Some data stays in a warehouse, some in a lake, some in operational systems.
  • The fabric helps teams discover, connect, govern and access it.

Why it matters: a fabric can work across a distributed environment. It does not require one central data store.

Myth11.5 “Mesh and fabric are competitors”
§11.5 · p. 66

Reality

  • They are not necessarily competing choices. They address different parts of the problem.
  • Mesh: ownership and responsibility.
  • Fabric: connecting, finding, governing and accessing data across systems.
  • An organization can use both. Domain teams can own data products through a mesh approach, while fabric capabilities connect those products with data in other systems.

Why it matters: they answer different questions.

Myth11.6 “Open formats eliminate platform lock-in”
§11.6 · p. 67

Reality

Open formats make it easier to use data across tools. They do not remove all platform dependencies. An architecture can still depend on platform-specific features, governance tools, compute engines, APIs, security systems and workflow tools. Using an open table format does not mean the whole platform can be replaced without changes.

Why it matters: open formats improve interoperability, but interoperability is not the same as complete portability.

Myth11.7 “One modern platform means one architecture”
§11.7 · pp. 67–68

Reality

Putting many capabilities on one platform does not create one architecture. A single platform can support several patterns at once: lakehouse storage, SQL analytics, streaming, ML / AI, governance and data sharing. The organization can still use different patterns for different needs.

Why it matters: a platform provides capabilities. The architecture decides how those capabilities are used.

Myth11.8 “Medallion architecture is the same as lakehouse architecture”
§11.8 · p. 68

Reality

They are related but not the same. A lakehouse is the broader technical architecture. Medallion Architecture is a way to organize data as it moves through the platform: Bronze → Silver → Gold. Each layer has a different purpose. Medallion can be used inside a lakehouse but it does not define the whole lakehouse.

Why it matters: one is the platform architecture. The other is a data organization pattern.

12Databricks perspective

12.1 How the pieces fit together

§12.1 · pp. 69–70

Databricks brings several of the discussed capabilities into one platform. I look at what each piece does.

  • Delta Lake provides the table and storage layer.
  • Apache Spark handles large-scale data processing.

13Current 2026 terminology

Source §13 · pp. 73–78

Short entries. Open one to read it. The page search also finds terms here.

13.1 Open table formats
§13.1 · pp. 73

Modern platforms increasingly use open table formats on top of object storage. Examples: Delta Lake, Apache Iceberg and Apache Hudi.

They add table-level features that plain files do not provide. Depending on the format and engine: transactions, schema management, table metadata, time travel or versioning, and efficient reads and writes. That is one reason modern data lakes do more than store files.

But open format does not mean complete portability. A platform can still use its own compute, governance, security or management features. Open format = easier interoperability. It does not mean zero platform dependency.

13.2 Data products
§13.2 · p. 74

A data product is data prepared for others to use. It is more than a table in storage. A useful one usually has a clear owner, a clear purpose, known users, quality expectations, documentation and access rules.

Data products matter most in data mesh, where domain teams own the data they produce. Example from the source: the Sales domain provides a Sales Performance data product for reporting or analysis.

A data product treats data as something other teams can depend on. The exact meaning varies between organizations, so I check how the term is used each time.

13.3 Semantic layer
§13.3 · pp. 74–75

A semantic layer gives business meaning to data. Users do not need to understand raw tables and technical column names. It provides common definitions for things like revenue, customer, order, profit and active user.

Example: two teams may calculate "revenue" differently if they use different tables or filters. A semantic layer gives them a shared definition. It also helps BI tools and other applications use consistent business metrics.

It is not the same as the warehouse or lakehouse. The lakehouse or warehouse stores and processes the data. The semantic layer gives the data a common business meaning. The design varies between platforms and organizations.

13.4 Data mesh
§13.4 · p. 75

Data mesh is still mainly an organizational and sociotechnical approach. Core ideas: domain ownership, data as a product, self-service data infrastructure, federated governance.

It is not tied to one storage technology. A company can build these ideas on a lakehouse, a warehouse, multiple platforms or a mix. Data mesh describes how ownership and responsibilities are organized. It does not prescribe one technology stack.

13.5 Data fabric
§13.5 · p. 76

Data fabric still describes an approach for working with data across systems. It can include data integration, discovery, metadata, governance and data access.

The exact meaning is not always the same. Some vendors use it as a broad term for a connected data environment. Some research uses it more specifically for the technologies and practices that connect and manage distributed data. I check the context before assuming what someone means.

13.6 Federation and virtualization
§13.6 · pp. 76–77

These terms are related to data access, not data storage.

  • Federation: I can work with data that stays in different systems.
  • Virtualization: users or tools can access that data without first creating another physical copy.

Example: data stays in a CRM, warehouse or another database while a query or data service reaches it there. That can reduce data movement in some designs. But there are limits. Performance, security, network access and source-system capabilities still matter.

The data does not have to move just because I need to use it.

Added context · checked 8 Nov 2026

Databricks documents Lakehouse Federation as a way to query external systems in place. Its query federation sends JDBC queries to relational databases such as MySQL, PostgreSQL and Snowflake, and it does not allow writes. Its catalog federation reads tables in external catalogs such as AWS Glue or Hive Metastore directly from object storage. This is one vendor's implementation. Other tools vary.

13.7 Medallion architecture
§13.7 · p. 77

Medallion Architecture is a way to organize data as it moves through a platform: Bronze → Silver → Gold.

  • Bronze: raw or lightly processed data
  • Silver: cleaned and refined data
  • Gold: data prepared for specific business use

I keep it separate from the lakehouse. Lakehouse = the broader platform architecture. Medallion = a way to organize the data. Databricks describes the layers in What is the medallion lakehouse architecture?

13.8 Unified governance
§13.8 · pp. 77–78

Modern platforms often bring governance into one shared layer: access control, data discovery, lineage, auditing, data classification and data policies. The goal is to make these controls work across the environment.

Unified governance does not mean every system must be the same. An organization can have a warehouse, a lakehouse, SaaS systems and other sources and still use common governance practices across them. Different systems can stay different while governance stays connected.

Added context · checked 8 Nov 2026

Databricks describes Unity Catalog as its governance layer for data and AI. It covers access control, lineage, auditing and discovery for the assets registered in it.

13.9 Interoperability
§13.9 · p. 78

Interoperability means different tools and systems can work with the same data or work together. Open table formats help. So do common APIs, data-sharing methods and standard interfaces.

It has limits. A system may use an open format and still depend on platform-specific features. So I separate two ideas:

  • Interoperability: systems can work together.
  • Portability: I can move from one platform to another with little change.

They are related but not the same.

14Why the same term can mean different things

Source, unnumbered · pp. 79–80

Data architecture terms do not have one fixed definition. Vendors, researchers and engineering teams use the same term in slightly different ways.

  • Data fabric is sometimes a broad idea for connecting and governing data across an organization. Other sources use it more narrowly.
  • Warehouses now support more data types and workloads.
  • Lakehouses now provide strong SQL and BI capabilities.

The boundaries are less strict. The concepts are still not the same. I ask what responsibility the architecture is describing:

  • Is it about where data is stored?
  • Is it about how data is processed?
  • Is it about who owns the data?
  • Is it about how different systems connect?

Different sources, different boundaries. One source may call data fabric a broad architecture approach. Another may focus on metadata, integration and access. The same happens with lakehouse and warehouse. A modern warehouse can support lake-style data and processing. A lakehouse can support SQL and BI that used to belong to warehouses.

So when I compare sources, I first ask: What does the source mean by the term? Then I compare actual capabilities and responsibilities. That works better than forcing every source into one fixed definition.

15Engineering takeaways

Source, unnumbered · p. 81

The main lesson: these architectures solve different problems.

  • A warehouse, lake and lakehouse describe different technical foundations.
  • Data mesh focuses on ownership and responsibility.
  • Data fabric focuses on connecting and accessing data across systems.
  • They can work together. Architecture does not have to be a choice between completely separate options.

The useful questions:

  1. What does the data look like?
  2. What workloads do we need?
  3. Who owns the data?
  4. Where does the data already live?
  5. What governance do we need?
  6. What systems do we already have?
  7. What will the architecture cost to run?

I do not choose an architecture because it is newer. I start with the engineering problem and then decide which responsibilities the architecture needs to handle.

The question I keep

Not "Which architecture is the newest?" but "Which architectural responsibilities does our system need to satisfy?"
