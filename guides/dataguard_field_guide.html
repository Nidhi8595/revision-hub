1.Project question and goal

From my notesSections 1–2, p. 1

I want to answer one question:

How can I build a data reliability platform on Databricks that automatically checks incoming data, finds schema and quality problems, stops unsafe code changes from reaching trusted tables, and helps me monitor and recover failed runs?

The goal is practical. I do not want to check everything by hand. DataGuard uses:

  • predefined data rules,
  • automated tests,
  • release checks,
  • and a record of failures, so I can investigate and recover.

Why a successful run is not enough

In real data engineering, a pipeline can finish successfully and still produce wrong results. Three things can go wrong:

  • Incoming files can have missing values, duplicate records, invalid measurements or an unexpected structure.
  • A code change can break a pipeline that worked before.
  • Nobody notices at once, so dashboards, reports and decisions are affected.

DataGuard combines validation, automated tests, safe deployment checks, failure tracking and recovery in one small platform. The example use case is synthetic energy-meter data. Each record has a building ID, a meter ID, a reading timestamp and an energy consumption value.

Key idea

Run status and data correctness are two different questions. "The job is green" only says the code ran. It does not say the data is right.

A real example from my own run

My first delivery registry marked BATCH_001 as a duplicate of BATCH_003, and every job still succeeded. The cause was a timezone mix-up in the manifest timestamps (see Step 5). The pipeline was healthy. The decision was wrong.

5.Architecture overview

From my notesSection 6, pp. 4–5

The platform receives synthetic energy-meter data and keeps the raw input. It validates the data against defined rules and separates accepted records from rejected ones. Trusted data becomes Gold tables for reporting. In parallel, code changes go through automated tests and release checks before deployment. Operational tables and dashboards make the behavior visible.

Key idea

Key design rule: a bad data batch and a bad code release are different problems. I handle data-quality failures by severity and by the contract. Critical code or schema incompatibilities must fail the relevant release checks.

Added context

The Bronze, Silver, Gold split follows the medallion architecture. It describes data layers that go from raw to validated to enriched, and each layer improves quality step by step.

Synthetic energy-meter data

I wrote a Python script that makes 1,000 synthetic readings across several buildings, meters, timestamps and ingestion batches. It adds problems on purpose: missing values, negative consumption, invalid numeric values and duplicates.

What the script does:

  • Imports tools for files, random numbers, folders and dates.
  • Locks the random seed, so the data is identical on every run.
  • Prepares the output file energy_readings.csv and creates the folder if needed.
  • Defines five columns: building ID, meter ID, timestamp, energy consumption, batch ID.
  • Generates 1,000 records with random building and meter IDs, timestamps spaced 15 minutes apart, and consumption values.
  • Injects errors: negative values, blank fields, text instead of numbers, duplicate rows.
  • Shuffles the rows so the errors are scattered.
  • Writes the CSV and prints the total record count.

9.Step 3: Local validation engine

From my notesStep 3, pp. 14–22

I built a reusable Python validation engine. It loads my contract and:

  • checks schema compatibility,
  • checks required fields and data types,
  • finds invalid timestamps and consumption values,
  • finds duplicates using the business key,
  • separates accepted from rejected records and records clear rejection reasons.

Schema compatibility results are reported separately, so I can plug them into release-safety checks later.

How the engine works

Contract loader. load_contract() finds data_contract.json in the config folder. A ROOT path goes two levels up from the script. The function reads the file and turns the JSON into a dictionary.

Schema check. It compares dataset headers with the contract, using sets so Python can subtract one from the other. It reports missing columns and unexpected extra columns. It returns a list of schema errors, or an empty list.

Record check (validate_record).

  • It checks that required fields exist and are not empty. If one fails, it stops early and returns the errors.
  • It checks types (timestamp, double, string). A try/except catches conversion errors, like text where a number should be.
  • It flags consumption below the minimum as a negative consumption error.
  • It builds a key from the contract's unique_key columns. If the key was already seen, it logs a duplicate error. Otherwise it adds the key to a seen set.
  • It returns the full list of errors for that record.

Main run. It loads the contract and the CSV, validates the headers, loops through every row and sorts it into an accepted or rejected list. Then it prints the totals and up to ten sample rejection reasons.

Added context

This order is the local validator's order. The Databricks Silver layer (Step 4) evaluates all checks and combines the reasons into one validation_reason, so one record can carry more than one reason there. Also, the Silver layer treats unexpected source columns caught in _rescued_data as a reason to reject.

Automated tests with pytest

I started with tests for a valid record, negative consumption, a missing meter ID and a duplicate reading. The duplicate test sends the same row through the validator twice with a shared seen set. The second pass must report Duplicate reading.

Python
from dataguard.validator import load_contract, validate_record

def test_valid_record():
    contract = load_contract()
    seen = set()
    row: dict[str, str] = {
        "building_id": "B001",
        "meter_id": "M001",
        "reading_timestamp": "2026-10-28T09:00:00",
        "energy_consumption": "12.5",
        "source_batch_id": "BATCH001",
    }
    assert validate_record(row, contract, seen) == []

def test_negative_consumption():
    contract = load_contract()
    row: dict[str, str] = {
        "building_id": "B001",
        "meter_id": "M001",
        "reading_timestamp": "2026-10-28T09:00:00",
        "energy_consumption": "-5",
        "source_batch_id": "BATCH001",
    }
    errors = validate_record(row, contract, set())
    assert "Negative energy consumption" in errors

Bronze: bronze.py

Bronze keeps the data as it arrived. My code reads the CSV as a stream with Auto Loader (cloudFiles), uses a declared all-string schema and turns on rescue mode.

Python
from pyspark import pipelines as dp
from pyspark.sql.functions import current_timestamp, col
from pyspark.sql.types import StructType, StructField, StringType

SOURCE_PATH = "/Volumes/dataguard/sample_data/dataguard_files/energy_readings.csv"

raw_schema = StructType([
    StructField("building_id", StringType(), True),
    StructField("meter_id", StringType(), True),
    StructField("reading_timestamp", StringType(), True),
    StructField("energy_consumption", StringType(), True),
    StructField("source_batch_id", StringType(), True),
])

@dp.table(
    name="dataguard.bronze.bronze_energy_readings",
    comment="Raw energy meter readings with ingestion metadata.",
)
def bronze_energy_readings():
    raw_data = (
        spark.readStream.format("cloudFiles")
        .option("cloudFiles.format", "csv")
        .option("cloudFiles.schemaEvolutionMode", "rescue")
        .option("rescuedDataColumn", "_rescued_data")
        .option("header", "true")
        .schema(raw_schema)
        .load(SOURCE_PATH)
    )
    return (raw_data
        .withColumn("ingested_at", current_timestamp())
        .withColumn("source_file", col("_metadata.file_path")))

Re-typed from my screenshot of bronze.py; I rewrapped the final return line for reading.

Why this design:

  • Raw values stay. Even an invalid value like "abc" remains available for Silver to validate.
  • Ingestion is tracked. I add an ingestion timestamp and the source file path.
  • Ingestion is incremental. Auto Loader finds newly arriving files.
  • Unexpected columns are caught. Rescue mode captures data that does not match the declared schema instead of treating it as an expected field.
Added context

Auto Loader processes new files as they arrive. In rescue mode the schema is never evolved and the stream does not fail on schema changes. Unexpected data goes to the rescued data column.

Auto Loader only processes files it discovers, so my CSV had to be in place before the first run.

Silver: valid records and quarantine

Silver reads Bronze and makes two outputs:

  • dataguard.silver.silver_energy_readings: valid, cleaned records.
  • dataguard.silver.quarantined_energy_readings: rejected records and their reasons.

It also detects duplicate business keys and safely converts the raw strings into timestamps and numbers.

Rules I wrote down for Silver:

  • Read the Bronze streaming table, then validate required fields, timestamps and numeric consumption.
  • Reject negative values, NaN and infinity, and null or blank required fields.
  • Reject unexpected source columns captured in _rescued_data.
  • Records without a valid business key are quarantined for their real errors. They are not wrongly called duplicates.
  • If a valid and an invalid record share a key, the valid one is preferred.
  • Keep only one record per valid business key across the available Bronze history, using a deterministic order (source metadata and a content hash).
  • Give duplicates their own quarantine reason.
  • Use the same validation logic for both outputs, so one record cannot be accepted by one output and rejected by the other.
  • Use batch reads for full-history deduplication.

Local validator vs Silver. Both cover the same requirements.

Requirement Local validator Silver
Required fields Yes Yes
Data types Yes Yes
Invalid timestamps Yes Yes
Negative consumption Yes Yes
Duplicate business key Yes Yes
Unexpected columns Yes Yes
Rejection reasons Yes Yes

They are separate implementations on purpose. validator.py uses Python's CSV reader on single dictionaries. silver.py works on distributed Spark DataFrames in a managed pipeline. Running the local validator inside every Spark transformation would add driver-side work and would not scale.

Limitations I noted
  • Full-history deduplication: my materialized view evaluates the whole available Bronze dataset, keeps one record per business key and quarantines the rest.
  • Schema changes: rescued-data handling captures unexpected fields, but I still need to test an altered-schema CSV to confirm the exact behavior.
  • Business-key policy: the contract defines uniqueness with building_id, meter_id and reading_timestamp. I must keep that definition the same in both validators.

11.Step 5: Idempotency and recovery

From my notesStep 5, pp. 33–64

This step matters most. DataGuard must not only process data right once. It must also behave right when the same data arrives again, a pipeline fails, or a corrected batch arrives.

Two ideas of identity

Identifier Purpose
source_batch_id The source batch recorded inside an individual reading
ingestion_batch_id The actual file/batch delivered to DataGuard

For example, the incoming file energy_readings_20261030_001.csv becomes ingestion_batch_id = 20261030_001. I keep my source data unchanged and add a separate ingestion identity in Bronze, so I never overwrite the evidence of what I received.

How I treat deliveries:

  • First delivery → process.
  • Same delivery again → recognize it.
  • New delivery → process as a new batch.
  • Corrected delivery → process as a new version and apply the correction policy.
Identity What it identifies How
Delivery identity An incoming file A content hash, so an identical file is recognized under a different filename
Reading identity One reading The business key building_id, meter_id, reading_timestamp

If a corrected delivery has the same reading identity but a different consumption value, it becomes a new version of that reading. The original stays for audit, and Gold uses the latest accepted version.

Contract update

I extended the contract and kept all existing rules. The new batch_processing section states the policy.

JSON
"batch_processing": {
  "delivery_identity": "ingestion_batch_id",
  "duplicate_delivery_detection": "content_hash",
  "correction_policy": "new_batch_preserve_history",
  "reading_version_key": ["building_id", "meter_id", "reading_timestamp"],
  "latest_accepted_version_wins": true
}

Re-typed from my screenshot of the updated contract.

Generating uniquely identifiable batches

A generator script takes --batch-id and --records (default 1,000). It writes a CSV and a JSON manifest with the batch ID, record count and a SHA-256 file hash. I ran it for BATCH_001, which gave 1,000 records.

PowerShell
python data/generate_sample_data.py --batch-id BATCH_001
Added context

hashlib in Python's standard library includes SHA-256. Two files with the same bytes give the same hash, whatever their names are.

Local batch registry (SQLite)

I first built and tested my idempotency rules locally before building the Delta equivalent. I used SQLite because it gives persistent storage and transactional updates without extra packages.

Function What it does
connect Opens the database and creates batch_registry if missing (IDs, names, hashes, status, timestamps)
register_batch Reads the manifest. If the batch ID exists with different content → error. Exact match → skip as already registered. If the same hash exists under another batch ID → DUPLICATE. Otherwise RECEIVED. Saves the batch
update_batch_status Checks the change is allowed (for example RECEIVED → PROCESSING → PROCESSED), then updates the status and completion time
get_batches Returns all batches sorted by received time
Status Meaning
RECEIVED New delivery registered
PROCESSING Processing started
PROCESSED Processing completed
FAILED Processing failed; retry allowed
DUPLICATE Identical content already registered

The registry database is runtime state, not source code, so I added it to .gitignore. I keep code and tests in Git, not the local database.

What my experiment proved. I registered two batches and then a third with the same content as the first.

  • Different batch IDs do not automatically mean different data.
  • Different filenames do not automatically mean new data.
  • SHA-256 content hashing identifies identical deliveries.
  • The registry keeps the duplicate delivery and records which original it matches.

Idempotency tests

I turned the experiment into repeatable pytest tests. A helper, create_manifest, builds fake manifests.

Test What it proves
Register new batch A new batch gets RECEIVED
Detect duplicate content A second batch with the same content is DUPLICATE
Same batch registration is idempotent Registering the same batch twice returns ALREADY_REGISTERED, no crash
Same batch ID with different content is rejected Reusing an ID with changed content raises an error
Failed batch can be retried A failed batch can go back to processing and finish as PROCESSED
Processed batch cannot be reprocessed A finished batch cannot restart or change
Corrected delivery is registered as new batch New contents under a new batch ID register normally

I ran the full suite: 8 validator tests + 7 registry tests = 15 passed.

Limit I wrote down

The local SQLite registry shows the expected batch lifecycle, but it is not connected to my Lakeflow pipeline. I must not treat local tests as proof of distributed pipeline recovery or transactional Delta processing.

Bringing batch tracking into Lakeflow

I looked at my existing code and saw three issues:

  1. Bronze reads one specific CSV. To test many deliveries, Auto Loader must point at a dedicated incoming directory.
  2. Silver removes duplicates globally by business key. It does not keep several accepted versions of a corrected reading.
  3. Gold reads Silver's accepted records. Once I keep reading history, Gold must aggregate only the current accepted version.

To avoid disturbing the working pipeline and its checkpoint, I created a separate Phase 5 flow with a new incoming directory and a separate Phase 5 Bronze table. BATCH_003.csv is an exact copy of BATCH_001.csv. That gives me a controlled duplicate-delivery experiment. I uploaded the two batch manifests so I can find duplicates by content_hash even under different filenames.

Phase 5 Bronze joins each CSV row with its manifest by file name:

CSV files → Auto Loader → filename matching → manifest metadata → Bronze

multiLine=true makes Spark read each manifest file as one JSON object. These columns are added:

Column Purpose
ingestion_batch_id Identifies the actual file delivery
content_hash Identifies identical file content
record_count Expected records from the manifest
batch_created_at Delivery creation time
manifest_match_status Shows whether the manifest was found

The run ingested 2,000 records from the two CSV files. The original Phase 4 Bronze, Silver, quarantine and Gold tables stayed unchanged. Both batches had the same content hash, which proved that two differently named deliveries can hold identical data.

The delivery registry in Databricks

I built a registry table from the manifests. It keeps every delivery but labels identical content as DUPLICATE.

  • It reads the JSON manifests and turns the creation date into a timestamp.
  • It groups files with the same content hash, ordered by creation time and batch ID.
  • It picks the first batch for each hash as the canonical batch.
  • A batch that matches the canonical one is ACCEPTED. Any other is DUPLICATE.
  • It saves the canonical batch in duplicate_of_batch_id for each duplicate.

Lesson: a timestamp needs a timezone

My first registry result was wrong. It marked BATCH_001 as the duplicate of BATCH_003.

Batch created_at as stored What happened
BATCH_001 2026-11-02T10:30:58.364497 (no timezone) The value was local Indian time, but Spark read it in the session timezone (UTC), which shifted the ordering
BATCH_003 2026-11-02T05:59:30.520+00:00 (timezone-aware) Read correctly

A timestamp is only useful for ordering events when its timezone and meaning are consistent. In production I would normalize timestamps to UTC at ingestion and keep created_at separate from the real received_at delivery time.

My later results show BATCH_001 as ACCEPTED and canonical, with BATCH_003 as DUPLICATE. A manifest screenshot also shows created_at with a UTC Z suffix (2026-11-02T05:00:58.364497Z).

Version note

My notes explain the cause and show the corrected result, but they do not describe the fix step by step. I infer that the manifest timestamp was regenerated in UTC. I will confirm that in the generator script. Also, 10:30:58 in India time (UTC+5:30) equals 05:00:58 UTC, which matches the corrected value.

The correction batch

I created BATCH_004 as a real correction and left BATCH_001, BATCH_002 and BATCH_003 untouched. The script reads BATCH_001.csv, finds the first valid row, lowers its energy value by 10%, sets the batch tag to BATCH_004, writes a one-record CSV, computes its hash and writes the manifest.

Databricks recognized BATCH_004 as a new delivery, not a duplicate. The Phase 5 Bronze streaming table processed only the one new record, which is what incremental ingestion should do.

Reading history in Silver

My design rules:

  • Duplicate delivery: exclude the whole batch from accepted reading history.
  • Duplicate reading inside one batch: keep one valid occurrence and reject the extra one.
  • Corrected reading in a new batch: keep it as a new version, even though its key already exists.

Silver for Phase 5 does these things:

  • It keeps only batches marked ACCEPTED, so BATCH_003 is out.
  • It parses text timestamps and numbers safely.
  • It checks for missing or blank IDs, bad timestamps and unreadable numbers. It checks abs(consumption) == inf so an infinite value is invalid.
  • It flags negative values and builds one clear validation reason per row.
  • It does not deduplicate keys across batches. That is what keeps BATCH_004 available as a correction to BATCH_001.

Deduplicate inside each delivery. The window groups by batch, building, meter and timestamp. It orders clean rows before errors and older files before newer ones. A row number marks the extras, and each extra gets Duplicate reading within delivery.

Delivery Reading key Energy
BATCH_001 B011 / M106 / same timestamp 138.73
BATCH_004 B011 / M106 / same timestamp 124.86
Key idea

Why I partition by ingestion_batch_id. Both rows above must survive because they belong to different deliveries. If I partitioned only by the reading key, BATCH_004 would wrongly look like a duplicate. Adding the batch ID deduplicates only within one delivery.

18.Revision prompts

Tap a question to reveal my answer.

Why can a pipeline succeed and still give wrong data?

The job only reports that code ran. Bad input, a broken rule or a wrong decision can still produce incorrect results. My timezone example showed a green run with the wrong canonical batch.

What is the difference between a bad data batch and a bad code release?

A bad batch is handled by contract severity and quarantine. A bad release fails release checks, such as critical tests or schema incompatibility.

Which key identifies a duplicate reading?

building_id + meter_id + reading_timestamp.

Why does Silver use the same logic for both outputs?

So a record cannot be accepted by one output and rejected by the other.

Why keep a local validator and a Spark Silver layer?

The local one uses plain Python on single dictionaries. Calling it from every Spark transformation would add driver-side work and would not scale.

How do I recognize a duplicate delivery?

By its SHA-256 content hash, not by filename or batch ID.

Why partition duplicate checks by ingestion_batch_id?

So a correction in a later batch is not mistaken for a duplicate.

What do history and current-state tables each give me?

History gives audit and traceability. Current state gives clean analytics with the latest accepted version.

Why did 976 history rows become 975 current rows?

One reading was corrected by BATCH_004, so it has two versions and only one is current.

Does deploying a bundle run the pipeline?

No. Deployment only creates the definition. I must run the pipeline to fill tables.

What did my rerun test not prove?

Recovery after checkpoint loss or in a completely new deployment.

Why use left joins in batch_delivery_metrics?

Every registered delivery must stay visible, including duplicates that contribute zero.
