    01What I am building

    A chatbot that answers only from a company handbook. It also shows the part of the handbook it used.

    An employee might ask, "How many leave days can I carry over?" The bot searches the handbook and answers from what it finds.p. 1

    LLMs do not know my company's documents. RAG (Retrieval-Augmented Generation) fixes that. The system first searches my documents for the most relevant passages. Then it gives those passages to the language model. The answer is grounded in real text.p. 1

    Vector search is the search step. It finds passages by meaning, not by exact words.p. 1

    Important

    I did not train a new model on the handbook. An existing model looks up my documents when someone asks. That is why new documents work without retraining.p. 56

    What I learn

    • How a PDF is split into chunks and stored in a Delta table
    • What embeddings are and how an AI Search (vector search) index uses them
    • How retrieval and an LLM combine into a RAG answer
    • How to test, deploy and call an agent on Databricks
    • How to put a simple Streamlit chat app in front of it
    Free Edition note

    Free Edition has limits. One AI Search endpoint per workspace and a small cap on serving endpoints.p. 1

    05Step 2 · PDF chunking

    Models and indexes work better with small passages than with a whole document.p. 2

    So I split the text into overlapping chunks. I use pypdf to read the PDF and langchain-text-splitters to split it. The RecursiveCharacterTextSplitter tries larger units like paragraphs first, then smaller ones.

    Extract text page by pagep. 12

    Notebook cell · python
    from pypdf import PdfReader
from langchain_text_splitters import RecursiveCharacterTextSplitter

# Read the handbook PDF
PDF_PATH = "/Volumes/hr_policy/hr_policy_data/hr_handbook_data/northwind_employee_handbook.pdf"

reader = PdfReader(PDF_PATH)

pages = []
for page_number, page in enumerate(reader.pages, start=1):
    text = page.extract_text() or ""
    pages.append({
        "page": page_number,
        "content": text
    })
    • enumerate(..., start=1) makes page numbers start at 1.
    • extract_text() or "" gives an empty string when a page returns no text.
    • Each page number is stored with its text. That lets me trace a chunk back to its page.

    I print the first 1,500 characters of the first page to check the extraction. The output said 2 pages.p. 13-14

    Split into overlapping chunksp. 14p. 17

    Splitter settings I continue with · python
    splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=100
)
    • chunk_size=500: each chunk is about 500 characters.
    • chunk_overlap=100: 100 characters repeat between neighbours. That keeps a topic connected when it continues into the next chunk.

    For each page I split the text and number each chunk from 1. I store the chunk's id, text and page number in a dictionary. That lets me find the source when the bot retrieves it.

    Added note

    The extraction and splitter cells are screenshots in my notes. The loop that builds the chunk records is only described in words. The record shape I show in section 14 comes from the later walkthrough.

    The first output was a DataFrame. It was not yet saved as a Delta table.p. 15

    Think about it

    What happens if chunk_size is 100? What about 5000? Which gives more useful passages, and why?p. 2

    Chunk size experimentp. 15-17

    I tested both sizes on the same handbook. I set the overlap to min(100, size // 5). That is the smaller of 100 characters or one fifth of the chunk size, so overlap stays small for small chunks.

    Comparing chunk sizes · python
    for size in [100, 5000]:
    test_splitter = RecursiveCharacterTextSplitter(
        chunk_size=size,
        chunk_overlap=min(100, size // 5)
    )
    test_chunks = []
    for page in pages:
        test_chunks.extend(test_splitter.split_text(page["content"]))
    print(f"\nChunk size: {size}")
    print("Total chunks:", len(test_chunks))
    for i, chunk in enumerate(test_chunks[:3], start=1):
        print(f"\nChunk {i}:\n{chunk}")

    Too small, balanced, too large

    The same equipment rule, cut three ways. This is an illustration of the idea.p. 57-59

    The rule is split into fragments. Each has only part of the meaning.

    • "Employees may request one keyboard"
    • "one mouse, and one headset"
    • "Requests must be submitted"
    • "through the IT service desk"

    Effect: if retrieval returns just one fragment, the model may not have enough to answer fully.

    Chunk · home-office equipment

    "Employees may request one keyboard, one mouse, and one headset for their home workspace. Requests must be submitted through the IT service desk. Additional equipment requires approval from the employee's department manager."

    Effect: enough information to answer, without too much unrelated text.

    One chunk holds remote-work deadlines, equipment requests, internet reimbursement and workplace security.

    Effect: a question about equipment retrieves the whole chunk. It has the right answer and several unrelated rules. This is what I saw in my app's source panel.p. 60

    Chunk size is something I test. I do not pick it at random.

    Overlap and its costp. 60

    Neighbouring chunks share a little text. If a split lands between two connected parts of a rule, the overlap keeps the link. The cost is repeated text. Too much overlap makes the index larger and can return duplicate or near-duplicate results.

    chunk_size is measured in characters here, not words. The splitter respects natural boundaries where it can, so chunks are not exactly the target size.p. 58

    Unclear in my notes

    The main build uses 500 / 100. The later walkthrough shows chunk_size=300 and chunk_overlap=40 as the setting for an updated chunking experiment. The last stretch goal says I still need to change the chunk size. I treat 500 / 100 as implemented and 300 / 40 as the next experiment.p. 58p. 52

    The splitter does not understand policies like a person does. It only tries to make more natural pieces.p. 61

    Limitation

    PDF extraction depends on how the PDF was made. A scanned page is just an image of text. extract_text() may not recover the words. I would need OCR.p. 61 The pypdf docs say pypdf is not OCR software.

    Concept illustration, not real output.

    The word "wine" may not appear in the policy. Keyword search looks for matching words. Vector search uses embeddings to find text with a similar meaning. It connects wine to alcohol.

    Three chunks give the chatbot a little more context. If the first chunk misses a detail, another may have it. Too many chunks can add irrelevant information.

    Search always returns somethingp. 26

    11How one question travels

    I follow one question through the app. "How early must I submit a remote-work request?"p. 70

    Retrieval finds evidence. The LLM turns that evidence into an answer. A fluent answer is not always a correct answer. That is why I test retrieval separately.p. 8

    The six steps in words
    1. The employee asks a question in Streamlit. The app also has the earlier conversation.
    2. The app calls the deployed agent. app.py uses DatabricksOpenAI and client.responses.create(...).
    3. The agent decides to retrieve. It uses the AI Search retrieval tool.
    4. AI Search returns matching chunks. For this question, the rule is at least five business days before the start date.
    5. The language model writes the answer from the chunks and its instructions.
    6. Streamlit shows the answer. It separately queries the index to show source passages in an expandable section.

    Session state and conversation historyp. 74
    Session state · python
    if "messages" not in st.session_state:
    st.session_state.messages = []

    Streamlit reruns the script when users interact with widgets. Session State keeps variables across those reruns for each user session. Without it the chat would vanish after each question.

    A saved record looks like {"role": "user", "content": "How early must I request remote work?"}. An assistant message can also keep the source passages and the response time. The clear button empties the list and reruns the app. This is session history, not a permanent database.

    ask_agent()p. 74
    The core call · python
    response = client.responses.create(
    model=ENDPOINT_NAME,
    input=input_messages
)
    • client is my connection to the Databricks-hosted agent API.
    • ENDPOINT_NAME identifies the deployed HR agent endpoint.
    • input_messages holds the relevant history and the new question.
    • response.output_text returns the text when available.

    This function does not read the PDF or create chunks. That work is already done. It only sends the request to the agent.

    get_source_passages()p. 75
    Direct index query · python
    results = w.vector_search_indexes.query_index(
    index_name=VECTOR_SEARCH_INDEX,
    columns=SOURCE_COLUMNS,
    query_text=question,
    num_results=keep,
)

    In plain words it asks AI Search: find the passages most relevant to this question from my index. Then it collects their text and shows it in an expandable section.

    It is separate from ask_agent() because the UI needs the passages. The trade-off: this second query can return different passages from the agent's own retrieval. To guarantee exact citations I would capture the agent's real retrieval results and pass them through, instead of searching twice.

    Chat handling, status and typing effectp. 75
    1. Get the user's question.
    2. Save it in session state.
    3. Call the agent.
    4. Retrieve source passages separately.
    5. Show the response and the source panel.
    6. Save the assistant message for later display.

    I also added a status message, a response-time measurement and a typing effect. They improve the experience. They do not make answers more accurate.

    show_sources()p. 75

    It loops through the returned passages. It shows the passage number, the document and page when available, and a similarity score when the index returns one.

    Remember

    The score is a search signal. It is not a percentage guarantee that the passage is correct. It does not prove the agent used that passage.

    I use HTML escaping so document text is not read as raw HTML in my custom source cards.

    Sidebar and welcome cardsp. 76

    The sidebar has example questions, a conversation download and a clear action. The welcome screen shows clickable topics when there are no messages.

    These buttons set a pending question in session state. The app reruns and handles it through the same chat flow as a typed question. So the sample buttons need no separate agent code.

    def get_source_passages(question):
    """Retrieve relevant source passages from the AI Search index."""
    workspace_client = WorkspaceClient()

    results = workspace_client.vector_search_indexes.query_index(
        index_name=VECTOR_SEARCH_INDEX,
        columns=SOURCE_COLUMNS,
        query_text=question,
        num_results=3,
    )

    if not results.result or not results.result.data_array:
        return []

    column_names = [column.name for column in results.manifest.columns]
    passages = []
    for row in results.result.data_array:
        record = dict(zip(column_names, row))
        content = record.get("content")
        if not content:
            continue
        passages.append({
            "content": content,
            "document": record.get("document", "Source document"),
            "page": record.get("page", "Not available"),
        })
    return passages

    14Concepts I need to remember

    The reasons behind the steps.

    Why chunking existsp. 57-58

    Say the handbook has 100 pages. I do not send all 100 to the model for every question. That adds noise, hides the key rule and may exceed the model's input space. I prepare the document first. Then I retrieve a few relevant passages per question.

    Too large

    More unrelated text in each result.

    Too small

    Parts of one rule get separated.

    Suitable

    Enough to answer, without too much extra.

    Why Delta first, and the MERGE trapp. 62-63

    The Python list chunks vanishes when the notebook stops. The Delta table is my durable knowledge base. The save cell checks if the table exists. If it does, it merges on the chunk id.

    Merge on chunk id · python
    delta_table.alias("target").merge(
    chunks_df.alias("source"),
    "target.id = source.id"
).whenMatchedUpdateAll().whenNotMatchedInsertAll().execute()
    • The incoming id already exists: update that row.
    • The incoming id is new: insert it.
    Limitation

    This MERGE does not delete old chunks that no longer appear in the new output. If a new chunk size makes fewer chunks, obsolete rows stay. A reliable rebuild must remove or reconcile them before I sync the index. Changing chunking settings is not enough by itself.p. 63

    Docs check · Nov 2026

    The merge docs show a whenNotMatchedBySource clause that can delete target rows with no match in the source. That is a documented option for this cleanup. My notes did not use it.

    Two ways to chunkp. 63-65

    Making an index from a Delta table does not split full documents into the chunks I want. In my design I create the chunks before I create or sync the index.p. 64

    Unclear in my notes

    AI Search, embeddings and triggered syncp. 65-66

    The index is a search-ready version of my chunks. Databricks uses the chunk text as the source and manages the embeddings. For example, "What can I get for my home office?" does not share words with "Employees may request one keyboard, one mouse, and one headset." The meaning is related. Semantic search connects them.

    1. I save chunks in the Delta table.
    2. AI Search reads the source table.
    3. The index processes the chunk text for searching.
    4. The index becomes available for queries.
    5. When the table changes, I trigger a sync.

    I use triggered sync. I ask for an update when I need one. So rerunning the notebook and syncing the index are two separate steps. Updating the table does not mean the index has refreshed.p. 66

    Retrieval returns a limited number of relevant chunks. My app asks for about three. That number is a setting, not a promise. Results depend on the text, chunk boundaries, search method and question. A correct equipment chunk can arrive next to a laptop-and-monitor chunk.p. 66

    Agent, index and filesp. 66-70

    AI Search finds information. The agent uses it to answer. A tool is something the agent can call. My retrieval tool lets it look up the handbook. Without it the model answers from general knowledge.p. 67 I test in Playground first. A poor answer there will not be fixed by a nicer Streamlit screen.

    Guardrails and access

    Added note · prompt instructions are not a complete authorization boundary

    My system prompt tells the model to answer only from the handbook. That shapes behaviour. It does not decide who may read which document. A model can fail to follow an instruction. Retrieved text can also carry instructions of its own.

    Real access control sits outside the prompt:

    • Index and endpoint permissions. AI Search uses access control lists for endpoints. It says each request is authenticated and authorized.
    • Least privilege for the app. The Apps resources page advises giving the app's service principal only what it needs. One example is Can query on a serving endpoint.
    • What goes into the index. My app uses its own deployed identity. Anyone who can open the app gets what that identity can retrieve. If I added restricted HR documents to the same index, every app user could get answers built from them.
    • Output checks. The source panel lets a person check the text. It is a help, not a guarantee.

    The handbook in this project is fictional and not confidential. The risk is about what I would do with real data.

    18Recap, prompts and glossary

    Seven things to rememberp. 79

    1. The PDFs are the source of truth. The app answers from them.
    2. Chunking prepares the content before indexing.
    3. Delta stores chunks. AI Search makes them searchable. Updating one does not refresh the other.
    4. The index retrieves. The agent answers.
    5. The notebook develops and deploys. agent.py defines the agent.
    6. Streamlit is the front end. app.py calls the deployed agent.
    7. A correct answer does not guarantee perfect sources.

    Revision prompts

    I answer first, then open the card.

    Why test retrieval with SQL before Playground?
    If the wrong chunks come back, the final answers will be wrong too.
    Why does the wine question find the alcohol rule?
    Embeddings match meaning, not exact words.
    What happens at chunk size 100? At 5000?
    100 gave 33 tiny chunks that lose context. 5000 gave 2 chunks that mix policies.
    Why can the France question still return three chunks?
    Vector search returns the closest chunks even when nothing is relevant. The prompt must make the bot decline.
    Why would the app return a 403?
    It lacks the serving endpoint resource with Can query.
    What does MERGE not do here?
    It does not delete rows that disappear from the new output.
    Why can the source panel differ from what the agent used?
    The app runs its own second query against the index.
    Why is a system prompt not enough for access control?
    It guides behaviour. Permissions must be enforced outside the model.
