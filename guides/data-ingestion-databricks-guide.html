Overview: how should data enter Databricks?

The source starts with one question. How should data enter Databricks?

It looks like a loading problem. It is not. Ingestion is where several architecture decisions begin.

  • A file in cloud storage does not behave like a production database.
  • A SaaS app does not expose data the way a Kafka topic does.
  • An app that generates events is a different problem again.
  • Sometimes the data does not need to move into Databricks at all.

So the hard part is not getting data from A to B. The hard part is deciding how the move happens, what the ingestion layer owns, and where that ownership sits.

The source links this to the "reference blog". Its point: the key question is not how many capabilities a platform has. It is how they fit together, and what my team still designs and runs.

Accuracy note

The source mentions a "reference blog" and a "supplied research brief" but never names them. I cannot check them. I only note them as the source does.

The source changes the problem

  • A file may land in cloud storage every hour.
  • A database may get thousands of row changes a day.
  • A SaaS app may expose customer records through an API.
  • An event-producing app may send telemetry nonstop.
  • An external database may already hold the data, so a query fits better than a copy.

The destination is the same. The ingestion problem is not. So I start with the source.

A simple mental model

Before I pick a mechanism, I ask six questions.

These questions lead me to a pattern, not to a product name. Recurring files may lead me to Auto Loader or COPY INTO. A database may need CDC or query-based ingestion. A supported SaaS source may fit Lakeflow Connect. Application events may use a push-based approach such as Zerobus. When the data need not be copied, Lakehouse Federation changes the architecture.

The first architectural question

One question is easy to skip: does this data need to move?

  • If yes, I design an ingestion path.
  • If no, I may be looking at a federation or query-based design.

This matters because every physical ingestion path adds work. Someone must manage connectivity, authentication, incremental processing, schema changes, failures, monitoring, and the impact on the source system.

So the goal is not to move everything into Databricks. The goal is a data path that fits the source, the latency I need, and how the data will be used.

Engineering insight (source): Start with the source, not the ingestion tool. Databricks has several ingestion approaches because sources create different engineering problems.

Foundations

Before Auto Loader, Lakeflow Connect, CDC, streaming or federation, I need a few basic ideas. The aim is to set the boundaries that make the patterns easier to read later.

What does ingestion mean?

At its simplest, ingestion gets data from a source into a place where it can be used. But the source shapes the process.

  • A file may already sit in cloud storage. It only needs to be discovered and loaded.
  • A database already stores tables. The real question is often how to find what changed.
  • A SaaS app exposes data through its own interfaces.
  • An event system keeps producing records.

These are all ingestion problems. They are not the same problem. The source type is the first architectural boundary.

Federation needs extra care. The data does not enter Databricks as part of the query. It stays in the external system.

The ingestion boundary

An ingestion pipeline crosses a boundary between two systems. The source is on one side. The Databricks environment is on the other. That boundary is more than a connection.

  • authentication
  • network access
  • source permissions
  • source-system impact
  • data discovery
  • schema changes
  • failure recovery
  • destination permissions

So I design ingestion as a system boundary. I do not treat it as a piece of code that reads data.

Batch and streaming are different operating models

Batch processes data in groups. A source may produce a file every night. The pipeline runs, processes what is there, and finishes.

Streaming works differently. Data keeps arriving. The pipeline keeps processing new records.

The key difference is not that streaming is "faster". Streaming brings state, checkpoints, failures, late-arriving data and continuous monitoring. So choosing streaming is choosing a different operating model.

Ingestion is not transformation

This matters as soon as the pipeline grows.

  • Ingestion asks: How does the data enter the platform?
  • Transformation asks: What should the data look like after it enters?

Ingestion builds a reliable path from the source. Transformation then cleans data, applies business rules, joins datasets and builds downstream models.

The source says the two layers can sometimes be built together. They still solve different problems. Keeping them apart stops ingestion code from becoming the place where every piece of business logic ends up.

Added: current docs

Added context (current docs): The medallion architecture page says the bronze layer should hold raw data with minimal validation. It also says Databricks does not recommend writing to silver tables directly from ingestion. This supports the source's point.

Ingestion is not federation

The source calls this the most important distinction in the foundations.

  • Ingestion: External source → ingestion → Databricks / Delta. The data moves.
  • Federation: Databricks queries the external system. The source data stays outside Databricks.

So federation is not just another ingestion mechanism. It is a different architectural decision. I stop asking "How should we move this data?" and first ask "Does this data need to move?"

The answer depends on the workload, latency needs, governance needs, source-system limits and how the data will be used. The source says its research brief makes the same split: ingestion moves data into the platform, and federation queries external data without copying it into Delta as part of the query.

Why these foundations matter

Once the boundaries are clear, the landscape is easier to read. A file problem looks different from a database change problem. A database change problem looks different from an event stream. An API extraction problem looks different from a managed SaaS connector. And federation may remove the ingestion problem altogether.

The next step is not to compare tools. It is to look at each source type and its engineering problem.

Architecture by source type

This is the main technical section. A file, a SaaS app, a database, an event stream and an API expose data differently. That affects discovery, change tracking, schema handling, latency, failure recovery, and how much engineering work I own.

3.1 Cloud files

Cloud object storage is one of the most common sources. A file lands in S3, ADLS or GCS. Databricks must discover it, read it, handle its schema and write it to a Delta table.

For recurring incremental file ingestion, I use Auto Loader. It keeps state about discovered files through checkpoints. It supports schema inference and schema evolution. Depending on configuration, unexpected data can be rescued instead of failing the whole ingestion.

Auto Loader

Auto Loader helps when files keep arriving and I want Databricks to process only new ones. The important idea is state. The process must remember what it has discovered and processed. Checkpoints hold that state. They also support recovery when the streaming query restarts.

Added: current docs

Added context (current docs): The Auto Loader page says file metadata is stored in a key-value store (RocksDB) inside the checkpoint location. It has two file detection modes: directory listing and file notification. It does not guarantee the order in which files are processed. It is compatible with Structured Streaming and Lakeflow pipelines, but it is not a fully managed connector.

COPY INTO

COPY INTO is another way to load files into Delta. It uses SQL. It fits a simpler batch pattern. I can run it again and again, and it is designed to avoid reprocessing files it already loaded.

  • Need recurring incremental file ingestion? Auto Loader is designed for that.
  • Need a straightforward SQL-based batch load? COPY INTO can fit.

Neither is better in general. The workload and operating model decide.

Added: current docs

Added context (current docs): The COPY INTO reference calls it a retryable, idempotent operation. Files already loaded are skipped, even if they changed later. There are also common loading patterns.

3.2 SaaS sources

SaaS ingestion is a different problem. The source usually exposes data through an application API. So ingestion must handle authentication, incremental extraction, source-specific behavior, schema changes, retries and failures.

Lakeflow Connect offers managed connectors for supported SaaS apps. The managed approach cuts the connector and infrastructure work my team builds and runs.

The point is not the connector catalog. It is the operating model. A managed connector can take over much of the source-specific work. It does not mean I manage nothing. Authentication, permissions, networking, source behavior, data quality and downstream modeling still matter.

3.3 Databases

Database ingestion usually leads to two patterns: CDC-based ingestion and query-based ingestion.

  • With CDC, ingestion captures changes the source database exposes. Flow: Database → transaction log → CDC → Delta.
  • With query-based ingestion, a connector periodically queries the source. Flow: Database → scheduled query → Delta.

The difference matters. CDC rests on the source's change information. Query-based ingestion rests on reading the source with queries. They put different requirements on the source and behave differently in operation.

I do not say one always wins. I ask what the source can expose and what the workload needs.

Added: current docs

Added context (current docs): Lakeflow Connect now lists database connectors (CDC) and query-based connectors as separate types. The CDC connectors add an ingestion gateway and staging storage. Query-based connectors query the source on a schedule, with no gateway and no staging storage.

3.4 Streaming sources

Streaming sources bring another set of choices. Databricks provides Structured Streaming, managed streaming connectors and Lakeflow pipelines. These are not simple competitors. They are different levels of abstraction and control.

  • A managed connector handles more source-specific connection and ingestion work.
  • Lakeflow pipelines give a managed pipeline abstraction.
  • Structured Streaming gives direct access to the streaming programming model.

The exact choice depends on the source and workload. I pick the abstraction level that matches the control the pipeline really needs.

Added: current docs

Added context (current docs): The Lakeflow Connect docs now list streaming connectors for message buses and event streams, and name RabbitMQ as an example. The source does not name specific streaming connectors, so I do not either.

3.5 APIs

An API can look simple from outside. Production API ingestion usually is not.

  • authentication
  • pagination
  • rate limits
  • retries
  • backoff
  • partial failures
  • schema changes

That is why I consider a managed connector first, when one exists and fits.

With no suitable connector, one useful design splits extraction from downstream processing: API → raw landing → processing. The extraction layer focuses on talking to the source reliably. Downstream pipelines focus on transformation and modeling. This is a pattern, not a rule.

Added: current docs

Added context (current docs): For sources with no managed connector, Lakeflow Connect also documents community connectors and custom connectors. I would check both before writing extraction code from scratch.

3.6 Zerobus

Zerobus is a different pattern. It is a push-based ingestion path for application and event-producing workloads. Databricks does not pull from a source again and again. The app or producer sends records straight toward Databricks ingestion.

This makes Zerobus relevant for application events and telemetry. The distinction is architectural.

The source warns that Zerobus is not a universal replacement for Kafka or other event infrastructure. The right choice depends on what the overall event architecture needs.

Added: current docs

Added context (current docs): The official name is Zerobus Ingest. The overview calls it a push-based streaming API that writes straight into Unity Catalog Delta tables. It lists SDKs over gRPC, a REST API, OpenTelemetry, MQTT and Kafka-compatible APIs as ways to send data. It also says that if I run Kafka for other consumers and want a copy in the lakehouse, managed streaming connectors fit better. Check regional availability before planning around it. An earlier official blog post announced a Public Preview. The overview page I read did not show a release label.

3.7 Federation

Now a different question: does the data need to move at all?

  • Ingestion: External source → data moves → Delta.
  • Federation: External source ← query ← Databricks. The data stays in the external system.

This makes Lakehouse Federation fundamentally different from ingestion. Sometimes the best ingestion decision is not to ingest.

Added: current docs

Added context (current docs): The docs describe query federation and catalog federation. Query federation pushes queries down to the foreign database over JDBC. Catalog federation reads foreign tables directly in object storage. The docs suggest federation for ad hoc reporting and proof-of-concept work on ETL pipelines. When a source supports both federation and Lakeflow Connect, they recommend Lakeflow Connect if high volume and low latency matter most.

Architectural trade-offs

Choosing a pattern is not only about whether data can reach Databricks. The better question: what does this choice make easier, and what does it make harder?

Each approach moves the trade-offs somewhere else. A managed connector may cut infrastructure work but give me less control. A custom pipeline may give more control but add code and operational duty.

Latency

How quickly do I need the data? A daily finance extract does not need the same design as app telemetry or an event stream. Batch fits scheduled intervals. Streaming fits continuous or low-latency needs. Streaming is not always better. The requirement comes first.

Source impact

How much load can I put on the source? It is easy to miss, because the pipeline runs in Databricks but the source still serves the data.

  • Database: query frequency, query complexity, connection usage, transaction-log retention, CDC overhead.
  • API: request limits, pagination, rate limits, authentication limits.
  • SaaS: the provider may set its own API or usage limits.

A design that works perfectly inside Databricks can still be poor if it puts too much pressure on the source.

Control

How much customization does the workload need? Managed ingestion cuts the connector and infrastructure code I run. Custom ingestion gives control over extraction logic, retries, scheduling, transformations, source-specific behavior and error handling. More control means more responsibility.

No position is right for every workload. It depends on how much source-specific behavior the application needs.

Schema change

What happens when the source changes? A new field may be harmless. A renamed field may break downstream logic. A type change may cause a serious compatibility problem. An unexpected value may expose a data-quality issue.

Schema inference, evolution and rescued data can automate part of the response. They do not remove the need to understand what the change means downstream. So I do not ask "Does this tool support schema evolution?" I ask "What happens to my pipeline when the source schema changes?"

Failure recovery

What happens when ingestion fails? Failures can happen anywhere: Source → Network → Ingestion → Destination. A source may go down. A network link may fail. A pipeline may restart. A batch may half finish.

  • Where is progress stored?
  • Can the operation be retried safely?
  • What happens to partly processed data?
  • How does the pipeline resume?
  • How do I find records or files that need attention?

State tracking and transactional writes can make recovery more predictable. Recovery still depends on the pattern. I design for failure before the first production failure.

Security

How do authentication, identity, networking and permissions work? Ingestion crosses a boundary, so security cannot be added after the pipeline works. I need to know:

  • how the source authenticates the connection
  • which identity runs the ingestion
  • which network path is allowed
  • which permissions exist on the source
  • where the destination data is written
  • who can access the resulting tables

A connector that can technically read a source may still not fit the organization's security model.

Operations

Who maintains the ingestion system? This grows in importance as sources multiply. A custom service may need me to maintain deployment, credentials, retries, monitoring, upgrades, API compatibility and failure handling. A managed connector cuts some of that. It does not remove operations. Someone still monitors the pipeline, investigates failures, manages access, tracks source changes and validates the data. The difference is where the work lives.

Cost

Cost is a set of drivers, not a label like "cheap" or "expensive".

  • compute
  • storage
  • network transfer
  • source-system usage
  • managed connector usage
  • pipeline execution
  • engineering and operational effort

A design that lowers Databricks compute may raise source load. A heavily customized pipeline may reduce reliance on a managed service and raise engineering effort. So I ask "What are the cost drivers for this architecture?" and not "Which is cheaper?"

Patterns and relationships

Ingestion is one part of a data platform. Once data enters Databricks, it joins a bigger design. Ingestion connects to medallion architecture, ETL/ELT, governance, change capture and data modeling. I keep the boundaries clear.

5.1 Ingestion + Medallion

Ingestion gets data into the platform. Bronze can keep the incoming data close to the source form. Transformation shapes it into easier structures. Silver and Gold are more refined data products. In short: ingestion gets the data in, transformation makes it useful.

5.2 Ingestion + ETL/ELT

They are related but ask different questions. Ingestion asks how data enters the platform. ETL/ELT asks where and when transformation happens.

The ingestion mechanism could be Auto Loader, a managed connector, CDC or something else. Transformation can be built separately. So changing the ingestion mechanism does not force a change to the business transformations. A database source can move to a new ingestion approach while the Silver and Gold logic stays the same in concept.

5.3 Ingestion + Unity Catalog

Ingestion also has a governance boundary. Unity Catalog is the governance layer around the data and its access.

  • Authentication: Can the ingestion process connect to the source?
  • Identity: Which identity performs the operation?
  • Network: Is the needed communication path allowed?
  • Ingestion: How is the data extracted and loaded?
  • Destination: Where does the data land, and who can access it?

So governance does not start after ingestion. The ingestion path has its own security and identity needs.

5.4 CDC + ingestion

CDC (Change Data Capture) is one way a source exposes changes. Instead of asking the database for its current state again and again, ingestion can read information about changes made at the source.

CDC is part of the ingestion design. It answers: "How do I capture changes coming from the source?" That differs from how those changes are later modeled or used.

5.5 CDF + ingestion

CDF (Change Data Feed) is different. It is a Delta Lake capability that exposes changes after data is already in Delta.

CDC and CDF can sit side by side in one architecture. They work at different boundaries. CDC deals with changes at the source. CDF deals with changes in Delta.

Added: current docs

Added context (current docs): The CDF page now describes two kinds: automatic CDF, which computes changes at read time using row tracking, and legacy CDF, which writes change data at write time and needs the table property above. The source does not split them. This is not an error in the source. It is newer detail.

5.6 SCD + ingestion

SCD (Slowly Changing Dimensions) is easy to mix up with CDC. SCD is downstream data modeling. An SCD Type 2 model can keep historical versions of a customer record.

Ingestion gets the source data in. SCD logic decides how that data is kept over time.

  • CDC = source-side change capture
  • CDF = Delta-side change exposure
  • SCD = downstream history modeling

All three can appear in one architecture. They answer different questions.

5.7 The bigger picture

Put it together: Source → Ingestion → Bronze → Transformation → Silver → Gold. Along the way, different technologies solve different problems.

  • Auto Loader handles incremental file ingestion.
  • CDC captures source-side database changes.
  • CDF exposes changes from Delta.
  • SCD models history for business entities.
  • Unity Catalog governs the data and its access.

None of them replaces the others. They work at different layers. That is the relationship to remember.

The Databricks perspective

The ingestion ecosystem can look like a long feature list: Lakeflow Connect, Lakeflow Pipelines, Auto Loader, COPY INTO, Structured Streaming, Zerobus and Lakehouse Federation. It is easier when I start with the problem each one solves. A file in cloud storage is not a Salesforce API, a database log or an event stream. So there is no single ingestion mechanism.

6.1 Lakeflow Connect

Lakeflow Connect gives managed ingestion for supported sources. Instead of building and running every connector, I use a managed path for supported SaaS apps, databases, files and streaming sources. Depending on the connector, it can cover parts of:

  • authentication
  • incremental extraction
  • schema handling
  • retries
  • connector infrastructure
  • ingestion orchestration

This cuts engineering work. It does not remove engineering duty. I still need to understand the source, permissions, network needs, data quality, schema behavior and downstream use. Connector availability varies by source and environment, so I check the current connector docs before I commit.

Added: current docs

Added context (current docs): The connector concepts page lists database (CDC), file, query-based, SaaS and streaming connectors, plus community and custom connectors. It says connectors are in various release states. The page was updated on 3 Nov 2026 when I read it. This matches the scope in the source.

6.2 Lakeflow Pipelines

Lakeflow Pipelines gives a managed way to build and run batch and streaming pipelines. I think of it as a pipeline abstraction. It does not replace every ingestion mechanism. A pipeline can use different ingestion patterns underneath. That separates how the source is ingested from how the pipeline is defined and run. It helps most when ingestion and transformation live in the same managed pipeline design.

Accuracy note

Name check: The current official name is Lakeflow Spark Declarative Pipelines (SDP). The docs also say "Lakeflow pipelines". Older material called it Delta Live Tables. The source uses "Lakeflow Pipelines". I keep that name here and treat them as the same product.

6.3 Auto Loader

Auto Loader stays important for cloud-file ingestion. Its job is narrow: find and process new files incrementally. It handles file discovery, state and schema behavior for recurring file ingestion. That makes it different from Lakeflow Connect. Lakeflow Connect is for managed connectors to supported sources. Auto Loader is for incremental file ingestion. They sit at different points in the architecture.

6.4 COPY INTO

COPY INTO is a SQL-oriented way to ingest files. It fits a straightforward load better than a continuously running incremental one. The choice between it and Auto Loader comes from the workload. I do not ask "Which is the modern tool?" I ask "What kind of file-ingestion workflow am I running?"

6.5 Structured Streaming

Structured Streaming is the lower-level streaming model. It gives direct control over streaming queries, source behavior, transformations, checkpoints and other streaming concerns. That helps when a workload needs custom behavior a managed layer does not offer. The cost is operational duty. More control means more of the streaming build is mine to design, test, monitor and maintain. It keeps a real role even as managed options grow.

6.6 Zerobus

Zerobus Ingest covers a different source pattern: a push-based path for apps and event-producing workloads.

This differs from a pull-based design where ingestion reads from a source again and again. It fits when the app or producer already generates events that must reach Databricks. It is not a universal replacement for Kafka or other event infrastructure. The surrounding event architecture still matters.

6.7 Lakehouse Federation

Lakehouse Federation sits outside the physical ingestion model. It queries supported external sources without first copying their data into Delta.

So it is part of the ingestion decision even though it is not ingestion. Sometimes the right design is to move the data. Sometimes it is to leave it where it is.

6.8 The move toward more managed ingestion

There is a clear direction toward more managed ingestion. Instead of every team building its own connector, retry system, schema handling and infrastructure, more of that comes as managed service. That changes where effort goes. I can spend more time on:

  • What data should I ingest?
  • How often should it arrive?
  • What should happen when the source changes?
  • How should the data be governed?
  • What should the downstream model look like?
  • Which failures need a human?

But managed does not mean automatic. A managed connector can cut infrastructure work. It cannot decide whether source data is correct, whether a schema change makes business sense, whether the source can take the load, or whether the resulting table is useful.

6.9 One ecosystem, different problems

The easy mistake is to expect one universal ingestion tool. Databricks does not have one, and does not need one. I look at the source first.

Anti-patterns

Ingestion problems often start before any code. The usual mistake is to start from the tool instead of the source and the workload. These are the patterns I watch for. Each one opens to show the question I should ask.

7.1 Custom API code when a managed connector exists

A custom API client means I own authentication, pagination, rate limits, retries, schema changes and monitoring. If a suitable managed connector already supports the source and the behavior I need, custom code may add work and solve nothing. Custom ingestion is not wrong. Sometimes the connector lacks the control I need.

Question: What does the custom build give me that the managed option cannot?

7.2 Moving data when federation would be enough

Sometimes I copy data only because that is what I usually do. If the workload only needs to query supported external data, physical ingestion may be unnecessary. With federation the data stays outside Delta. With ingestion it moves into Delta.

Question: Does this data actually need to move?

7.3 Treating every database problem as CDC

CDC helps when the source exposes changes in a way my architecture can use. Not every database workload needs it. Some can use query-based ingestion. The choice depends on:

  • how often the data changes
  • what latency I need
  • what the source supports
  • how much source load is acceptable
  • what change behavior the destination needs

The mistake is picking CDC before I understand the source and workload.

7.4 Heavy custom streaming code when a managed option is enough

Direct Structured Streaming gives control. It also means I own more of the build. If a managed connector or managed pipeline already fits, a lot of custom streaming code adds duty for no gain.

Question: What requirement justifies the extra control?

7.5 Loading data without thinking about source impact

The destination is Databricks, but the source still has to provide the data. A poor design can strain:

  • production databases
  • APIs
  • SaaS platforms
  • transaction logs
  • network connections

A technically valid pattern can still be a poor production design if it hits the source too hard.

7.6 Assuming schema evolution makes schema problems disappear

Schema evolution automates some changes. It does not automate schema design. A new column may be safe. A changed data type may not be. A renamed field may need downstream changes. An unexpected value may reveal a data-quality problem. Engineers still decide if the resulting data makes sense.

7.8 Treating every source like a file

A file is not a database. A database is not an API. An API is not an event stream.

  • Files are discovered.
  • Databases expose state and, in some cases, changes.
  • APIs expose requests and responses.
  • Event systems expose continuous records.

That difference should drive the design.

Quick recap and revision prompts

  • The source type is the first boundary. It shapes the ingestion problem.
  • Ask "does the data need to move?" before "which tool?".
  • Ingestion moves data in. Transformation shapes it. Federation leaves it in place.
  • Batch and streaming are two operating models, not fast and slow.
  • Managed cuts connector work. It does not cut responsibility.
  • CDC is at the source. CDF is in Delta. SCD is downstream modeling.
Revision prompt 1: Why does a daily finance extract not need the same design as telemetry?

Because latency should follow the workload. Batch fits scheduled data. Streaming fits continuous or low-latency needs. Streaming is not always better.

Revision prompt 2: What is the difference between CDC and CDF?

CDC captures changes at the source and brings them toward Databricks. CDF exposes changes after the data is already in Delta, for downstream consumers.

Revision prompt 3: When is federation the better answer?

When the workload only needs to query supported external data and does not need the data copied. The source says to ask whether the data must move before picking a tool.

Revision prompt 4: What does a managed connector still leave me to manage?

Authentication, permissions, networking, source behavior, data quality and downstream modeling. It also leaves monitoring, access and validation.

Revision prompt 5: Why keep business logic out of ingestion?

Ingestion builds a reliable boundary from the source. Business logic inside it makes the pipeline harder to change. A separate transformation layer lets me swap ingestion without touching Silver and Gold logic.
