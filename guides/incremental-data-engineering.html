Incremental Data Engineering: Full Loads, CDC, CDF & SCD

How should changing data be propagated through a data platform?

I use these notes to separate five questions. They look like one topic. They are not.

SOURCE from my PDF ADDED my explanation EXTERNAL official docs, checked 9 Nov 2026

1. The problem I start with SOURCE

I have a customer table with 100 million rows. Yesterday, only 5,000 customers changed. Some updated an address. A few were new. Some records were deleted.

My question is simple. Do I really want to process all 100 million rows again?

Sometimes yes. A full load can be simple, reliable and reasonable. It fits when:

  • the dataset is small
  • I need an initial copy
  • I need a complete snapshot

When a large dataset keeps changing, I do unnecessary work if I process everything again.

2. Incremental processing SOURCE

Instead of processing the whole dataset, I find what is new or changed. Then I process only that part.

That raises the next question. How do I know what changed? There is no single answer. I might use:

  • a timestamp
  • an increasing ID
  • a cursor
  • arriving files
  • a snapshot comparison
  • a proper CDC feed from the source system

EXTERNAL Two of these have named Databricks features. I use Auto Loader to incrementally process new files in cloud storage. I use AUTO CDC FROM SNAPSHOT to compare consecutive snapshots and build a synthetic change feed.

ADDED A timestamp or ID only finds rows that still exist. A hard delete leaves no row to find. I remember this when I pick a detection method. A proper CDC feed carries deletes as events.

3. What the target does with the changes SOURCE

Knowing what changed is not enough. I still decide what the target table does.

  • Should it keep only the latest value?
  • Should it keep older versions?
  • Should it apply inserts, updates and deletes automatically?

This is where MERGE, AUTO CDC, SCD Type 1 and SCD Type 2 come in.

4. Data already inside the lakehouse SOURCE

Things change when the data is already in the lakehouse. If a Delta table or a supported Iceberg table changes, Change Data Feed (CDF) can expose those row-level changes to downstream processing.

So CDF answers a different question from source-side CDC.

EXTERNAL Current docs describe two kinds of change data feed.

  • Automatic CDF. It computes changes when I read the table. It needs Databricks Runtime 19 or above. It works on Delta tables with row tracking and on Iceberg v3 tables.
  • Legacy CDF. It writes change records during table writes. It supports only Delta tables. I enable it per table.

I cannot use both on the same table.

5. The five questions SOURCE

These terms are related. They are not five versions of the same technology. I am not choosing between five competing tools. I am answering five different questions.

6. Customer-address example ADDED

The source talks about customers and addresses. I keep one customer for every diagram. Customer 101 lives in Pune. Later, the address changes to Mumbai.

Where the change starts: source-side CDC

Where CDF sits

EXTERNAL To turn on legacy CDF on a Delta table, I set a table property. Only changes made after this are recorded.

sql
ALTER TABLE customers
SET TBLPROPERTIES (delta.enableChangeDataFeed = true);

CDF rows carry a _change_type column. Its values are insert, update_preimage, update_postimage and delete. The docs recommend reading CDF with Structured Streaming.

python
(spark.readStream
    .option("readChangeFeed", "true")
    .table("customers"))

CDF is not a permanent history. Its records follow the table retention. If I need permanent history, I write the records to a new table.

7. Applying the changes EXTERNAL

Delta Lake MERGE supports inserts, updates and deletes. I wrote this example from the documented syntax. I did not run it.

sql
MERGE INTO customers AS t
USING customer_updates AS s
ON t.customer_id = s.customer_id
WHEN MATCHED AND s.operation = 'DELETE' THEN DELETE
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

The AUTO CDC INTO statement does the same job for a CDC feed. SCD handling is built in. The default is SCD Type 1. I adapted this example from the documented one. I did not run it.

sql (pipelines)
CREATE OR REFRESH STREAMING TABLE customers_history;

CREATE FLOW apply_customer_changes AS AUTO CDC INTO customers_history
FROM stream(cdc_data.customers)
KEYS (customer_id)
APPLY AS DELETE WHEN operation = "DELETE"
SEQUENCE BY sequence_num
COLUMNS * EXCEPT (operation, sequence_num)
STORED AS SCD TYPE 2;

ADDED MERGE is a general statement. AUTO CDC is built for CDC feeds. A hand-written SCD Type 2 with MERGE needs extra version logic. That is my reading of the docs. I did not build one.

The docs also cover advanced AUTO CDC topics, such as reading the change data feed of an AUTO CDC target table.

11. Revision prompts ADDED

What are the five questions? Which one does CDF answer?

How much, how I know what changed, where the change came from, how I apply it, how history is kept. CDF answers question 3 for lakehouse tables.

Why is CDC not the same as CDF?

CDC starts in a source system. CDF reports row-level changes of a lakehouse table. They sit in different places.

When is a full load a good choice?

When the dataset is small, when I need an initial copy, or when I need a complete snapshot.

What does SCD Type 2 keep that SCD Type 1 does not?

Older versions of a row. Type 1 keeps only the latest value.

Why can an out-of-order event hurt a MERGE?

MERGE applies what it sees. Without ordering logic, an old event can overwrite a newer one. AUTO CDC uses a sequencing column for this.

12. Glossary ADDED

Full load
Process the whole dataset again.
Incremental load
Process only what is new or changed.
CDC
A feed of row changes from a source system.
CDF
Row-level changes exposed by a Delta or supported Iceberg table.
MERGE
A statement that upserts or deletes rows by a match condition.
AUTO CDC
A pipeline feature that applies a CDC feed to a target table.
SCD Type 1
Overwrite. Keep the latest value.
SCD Type 2
Keep versions as separate rows.
Snapshot
The full state of a table at one point in time.
