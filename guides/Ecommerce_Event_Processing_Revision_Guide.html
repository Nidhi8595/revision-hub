Counting every event exactly once

A payment arrives twice. A shipment shows up before its order. An event has no ID. This guide follows 192 fake shopping events through a Databricks medallion pipeline and shows what the system did with each one, including where it fell short.

The story and the map

Imagine the shop’s app sends events: an order is created, a payment lands, stock moves, a parcel ships, a customer cancels. Networks retry, so some events arrive twice. Some arrive in the wrong order. Some are broken. Reports must still be right. The pipeline keeps the raw truth, checks it, then derives the current state.

Core idea. An event is not an order. One order produces many events. Keep the history, derive the latest state from it.

Silver: from checked to correct

Version 1 (streaming tables): the bug

A CASE expression named the first failing rule as quarantine_reason. Result: 189 valid, 3 quarantined. But GROUP BY event_id HAVING COUNT(*) > 1 found PAY-EVT-001 three times in valid events. The checks never compared rows with each other.

Version 2 (materialized views): the fix

SHA2(TO_JSON(NAMED_STRUCT('event_type',event_type,'order_id',order_id,
  'customer_id',customer_id,'amount',amount,'event_time',event_time)),256) AS payload_hash

event_stats AS (SELECT event_id, COUNT(DISTINCT payload_hash) AS versions
  FROM classified WHERE event_id IS NOT NULL AND TRIM(event_id) <> '' GROUP BY event_id)

-- quarantine_reason: MISSING_EVENT_ID, then versions > 1 => CONFLICTING_EVENT_ID, then validation_reason

valid_events: WHERE quarantine_reason IS NULL
  QUALIFY ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY event_time) = 1

Exact retries share a hash (one version), so QUALIFY keeps one. Same ID with different content has two hashes, so every copy is quarantined. Final: 193 classified, 187 valid, 6 quarantined (CONFLICTING 3, MISSING_ORDER_ID 1, INVALID_PAYMENT_AMOUNT 1, UNKNOWN_EVENT_TYPE 1).

Consequence worth noticing. The policy quarantines all three PAY-EVT-001 rows, including the legitimate original. The ORD001 history screenshot shows no payment event. Your PDF states the policy but does not discuss this cost.

Troubleshooting playbook

Seen in PDFPlausible

Duplicate event in valid_events seen

Symptom: PAY-EVT-001 counted 3 times. Cause: classification only validated each row alone. Fix: payload hash, version count, QUALIFY. Verify: re-run the HAVING query returns no rows.

Spark cannot infer a column type seen

A field holding only None has no type. Define the schema explicitly (StructType) before writing JSON.

Full recompute where you expected incremental seen

Not an error. Window functions and cross-row checks often recompute. Read the Incrementalization column instead of assuming.

Payment missing from an order’s history derived

Check quarantined_events for CONFLICTING_EVENT_ID on that payment’s id.

Run succeeds but numbers look wrong plausible

Success only means the code ran. Reconcile counts (193 = 187 + 6) and check business meaning (what IN_PROGRESS means).

Interview prep

Why keep duplicates in Bronze?

Bronze is the audit trail. You cannot investigate what you deleted. Follow-up, how do you then avoid double counting? Deduplicate in Silver.

Duplicate vs conflict?

A duplicate repeats the same content; a conflict reuses an ID with different content. The payload hash tells them apart. Follow-up, what is the downside of quarantining all versions? A legitimate original is also held back.

Why can a table show full recompute?

Logic that compares across rows, such as ranking or duplicate detection, is harder to refresh incrementally.

What would you add next?

Unmatched-payment flag, revenue and payment-status tables, stock checks, real received_at times, timestamp casting, a true failure and restart test.
