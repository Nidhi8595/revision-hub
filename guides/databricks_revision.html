WHERE vs HAVING — the report's #1 flagged interview question. WHERE filters rows and runs before grouping; it can't use aggregates directly. HAVING filters groups and runs after GROUP BY — that's why SUM(amount) > 50000 goes in HAVING, not WHERE.

What is Lazy Evaluation?
Transformations (filter, select, withColumn) don't execute immediately — Spark builds a plan and only runs it when an Action (show, count, collect) is called.
Does the notebook execute the SQL?
No — the notebook is only the interface. Compute provides the resources and Spark performs the actual execution.

The three aggregations I reach for constantly SUM · COUNT · COUNTDISTINCT

FunctionAnswersGotcha
sum()How much?—
count()How many rows?Rows ≠ orders if one order has multiple product rows
countDistinct(order_id)How many unique orders?Usually what the business actually meant
AOV — Average Order Valuesum(total_revenue) / countDistinct(order_id). Revenue tells you how much business happened. Orders tell you how much activity happened. AOV tells you how valuable one transaction is — Store A can out-revenue Store B on volume while Store B wins on AOV. Keep all three.

The LEFT JOIN lesson DON'T LOSE THE LEFT TABLE

customers
LEFT JOIN
orders
→
every customer appears, even with zero orders
"Show every customer, even if they never purchased" = LEFT JOIN, customers on the left. After the join, a zero-order customer gets NULL orders/revenue — coalesce those to 0, but leave last_order_date as NULL. 0 isn't a date; a customer who never ordered has no last order, and that's a meaningful NULL, not a bug.

Two mistakes I actually made LEARNED THE HARD WAY

MistakeFix
Double counting — count(*) on multi-row ordersUse countDistinct(order_id) when the question means "how many orders," not "how many rows"

Why did you create Gold tables?
To give downstream analytics and BI a business-oriented aggregate so they're not repeatedly processing transactional Silver data. Each Gold table has a specific grain — monthly, customer, category, channel, status, or city — and holds exactly the metrics that grain needs.
Why not just put every Gold table on the dashboard?
A dashboard is a visual answer to specific business questions, not an inventory of everything that exists. More charts isn't more insight — it's more scanning effort.

Change Data Feed (CDF) WHAT CHANGED?

Delta Table10,000 records
→
Change Data FeedINSERT · UPDATE · DELETE
→
Changed Recordse.g. 20 rows
Normal table = "what does the data look like now?" CDF = "what changed between versions?" Batch access via table_changes('table', start_version).
Important nuanceCDF is not the same thing as the CDC pattern used for Lakeflow streaming-table pipelines. table_changes() is a batch-style read of change info; Lakeflow's AUTO CDC is the mechanism for streaming CDC, and can implement SCD Type 1 or Type 2 behavior directly. Don't over-generalize this to "CDF can't be used with streaming" — CDF itself can be consumed by streaming mechanisms; it's specifically table_changes() that isn't the streaming-CDC pattern.

If interviewer asks… FLASHCARDS

ETL vs ELT?
ETL transforms before loading into the target. ELT loads first, then transforms inside the target platform — Databricks favors ELT because it has compute to transform after landing the data.
What is orchestration?
Coordinating the execution order and dependencies of multiple data-processing tasks — e.g. making sure Silver only runs after Bronze succeeds.
What problem does CDF solve?
It identifies row-level INSERT/UPDATE/DELETE changes so downstream processing can work on just the changed records instead of the whole table.
Does CDF implement SCD Type 2?
No — CDF only detects what changed. SCD logic decides how that change is represented in the target (overwrite vs preserve history).
SCD Type 1 vs Type 2, in one line?
Type 1 answers "what is the value now?" Type 2 answers "what was it before, and what is it now?"
Is table_changes() the same as Lakeflow CDC?
No. table_changes() is a batch-style read of change data. Lakeflow's AUTO CDC is the mechanism built for streaming-table CDC pipelines and can implement SCD Type 1/2 directly.

Row Filters TABLE-LEVEL, NOT QUERY-LEVEL

TABLE
↓
ROW FILTER FUNCTIONSQL UDF returning BOOLEAN
TRUE → row shown
vs
FALSE → row hidden
The practical build: CREATE FUNCTION department_filter(department STRING) RETURNS BOOLEAN RETURN department = 'IT', then attach it — ALTER TABLE employee_security_demo SET ROW FILTER department_filter ON (department). The other rows aren't deleted, they're just excluded from query results.

Row Filter vs WHERE clause SHARPEST DISTINCTION HERE

WHERE clauseROW FILTER
ScopeThat one query onlyAttached to the table itself
Bypassable?Yes — a plain SELECT * sees everythingNo — applies automatically to every query
Removaln/aALTER TABLE ... DROP ROW FILTER — always before DROP FUNCTION
Required privilegesSELECTEXECUTE on function + USE SCHEMA + USE CATALOG (row filtering doesn't replace normal table privileges — both are checked)
Why this mattersA WHERE clause is a promise the query makes. A ROW FILTER is a promise the table makes — it can't be bypassed just by writing a different query. Made user-aware with CURRENT_USER(), this becomes real fine-grained access control: admin sees all rows, an IT user sees only IT rows, and so on.
Does a row filter delete rows?
No — it restricts which rows are returned. The underlying data is untouched.
Why remove the row filter before the function?
Dropping the function first can leave an orphaned filter reference and make the table inaccessible — always DROP ROW FILTER, then DROP FUNCTION.

PAT vs Salesforce OAuth — Two Different Doors

The most common conceptual mistake, straight from the report: thinking a Databricks PAT will also authenticate to Salesforce. It won't.

Why does the pipeline never create new Salesforce Leads?
The project's job is to score and classify Leads that already exist in Salesforce — creating new ones would duplicate data the sales team already owns.
What keeps Genuine Score and Anomaly Score in sync?
They're two views of the same underlying signal set — high genuine-quality signals push the score toward Genuine, and the same weighted signals in reverse push toward Anomalous.

Delta Lake versioning & Time Travel

Version 0CREATE TABLE
↓ every DML/DDL adds an entry
Version 1, 2, 3…INSERT / UPDATE / DELETE / MERGE / ALTER
The transaction log records operation type, timestamp, user, and which data files changed. Normal queries always read the latest version; VERSION AS OF / TIMESTAMP AS OF (or shorthand @v1) read a specific past version. Old versions live for the retention window (default 30 days) until VACUUM cleans them up.
Use caseHow Time Travel helps
AuditingProve exactly what changed, when, and who did it
DebuggingCompare current version to yesterday's to find a bad write
RecoveryQuery the version before an accidental delete, restore from it

Medallion architecture — the less rigid version

Multiple Gold tables often share the same Silver tables. The pattern isn't fixed: some teams add a Platinum layer for ML features, others skip Gold and let analysts query Silver directly. The core principle stays constant regardless: separate raw ingestion → transformation → consumption. Bronze/Silver are shared infrastructure; Gold tables are usually built for one specific team, dashboard, or report.

Why a security token on top of a password? SELF-ANSWERED

A username + password authenticates the Salesforce user. The security token is an extra verification factor for API access — especially useful when the request comes from an untrusted network, which a Databricks notebook technically is from Salesforce's point of view. All three (username, password, token) go in a Secret Scope; none in the notebook.

The best lesson in the whole capstone DASHBOARD PARAMETER ≠ USER IDENTITY

What went wrong first: I built a Role dropdown (Sales Manager / Analyst / Data Engineer) on top of the real, row-filtered gold.sales_summary table. Selecting "Analyst" in the dropdown didn't change anything — the table still only returned South-region rows, because the row filter evaluates CURRENT_USER(), and the actual logged-in user was still the Sales Manager account. The dropdown is just a UI control; it has zero effect on who Unity Catalog thinks is asking.
gold.sales_summaryrow filter ON — real security
vs
gold.sales_summary_dashboardrow filter OFF — a plain copy, for demoing role switching
The fix: temporarily DROP ROW FILTER, CREATE TABLE ... AS SELECT * FROM sales_summary to snapshot an unfiltered copy, then immediately SET ROW FILTER back on the original. The dashboard points at the unfiltered copy and simulates roles with its own dropdown; the real table stays genuinely secured the whole time. Two tables, two jobs — one is truth, one is a demo.
One sentence for an interviewDashboard controls should never be confused with data-layer security — the real access control has to be enforced at the table with Unity Catalog row filtering, not trusted to a dropdown in the BI tool.

Write-back: one field, nothing else SIMPLE-SALESFORCE .UPDATE()

Lead_Score__c = 3 if LeadSource = 'Web' and Status = 'Open', else 1 — lower() + trim() first so "Web"/"web"/"WEB" all match. Verify the Lead IDs exist in Salesforce before writing, update just that one field via .update(), then check the change actually landed by opening the Lead in Salesforce itself.
Why did switching the dashboard Role dropdown not change the data?
Because the row filter checks the real authenticated Databricks user via CURRENT_USER(), not a UI parameter — a dashboard control can't impersonate a different identity.
Why not just drop the row filter permanently to make the demo easier?
That defeats the assignment's actual requirement — sales managers must only see their own region. The unfiltered copy exists purely for simulation; the production table stays protected.

RAG = Retrieval-Augmented Generation. An LLM doesn't know my company's Leads, policies, or tickets — RAG retrieves the relevant piece first, then hands it to the model as context. Vector Search finds by meaning, not exact words — "find content about unusual customer behavior" matches a document that never says the word "unusual," which keyword search would miss entirely.
Mosaic AI ≠ one LLM. It's Databricks' umbrella for Model development, Model Serving, Vector Search, Agent Framework, MLflow for GenAI, evaluation, AI Gateway, and Agent Bricks — governed underneath by the same Unity Catalog I already use for tables.

Vector Search vs Prompt Engineering — Vector Search answers "what information should I retrieve?" Prompt Engineering answers "how should the model use that information?" The LLM just generates the response; Evaluation decides if that response was actually good.
Tied to my own projectIf I built an assistant on top of Lead Anomaly Detection: user asks "why was Lead 10045 flagged?" → Vector Search retrieves that Lead's engagement/conversion numbers + the company policy on stale high-engagement leads → prompt says "use only the supplied context, don't invent information, cite the strongest indicator" → LLM explains it. That's a real GenAI architecture, not a chatbot demo.
Hallucinations: a confident-sounding answer that isn't actually supported by the retrieved context. A good prompt reduces this risk (supplied-context-only instructions, retrieval, evaluation, guardrails) but does not eliminate it on its own.

Why Random Forest, not one Decision Tree WISDOM OF THE CROWD

A single Decision Tree asks a sequence of yes/no questions ("payment_delays > 2?") that split customers into purer and purer groups, using an impurity measure like Gini to judge how good a split is. One tree can overfit to its particular training data. Random Forest trains many trees (here, 20), each seeing a different random sample of data and features, then lets them vote — the same reason you'd rather ask 20 people than 1 before trusting a judgment call.
Three-line summaryDecision Tree = one tree making decisions. Random Forest = many trees making decisions. Random = the trees are deliberately built differently so they don't all make the same mistake.

If interviewer asks… FLASHCARDS

What is lazy evaluation?
Transformations aren't executed immediately; Spark builds an execution plan and runs it only when an action is triggered.
PAT vs OAuth?
PAT authenticates to Databricks only. Salesforce OAuth (Client Credentials Flow) is a separate credential that authenticates to Salesforce. They are not interchangeable.
Bronze vs Silver vs Gold?
Bronze preserves raw ingested data as-is. Silver holds cleaned/validated data. Gold is aggregated, business-ready data for reporting.
WHERE vs HAVING?
WHERE filters individual rows before grouping and can't use aggregates directly. HAVING filters grouped results after GROUP BY.
CTE vs Subquery vs View?
Subquery — one-off, nested. CTE — readable, multi-step, still temporary. View — saved query, reusable across reports/dashboards.
Why Service Principal over User for pipelines?
A pipeline tied to a person's account breaks if that person loses access or leaves. A service principal is an independent, dedicated identity for automation.
Authentication vs Authorization?
Authentication answers "who are you?" Authorization answers "what are you allowed to do?" A valid token (auth) can still get a 403 (authz) if permissions are missing.
Why can Shuffle be expensive?
Operations like groupBy, join, distinct and orderBy may need matching data brought together across partitions — that movement costs network, disk, and sort time.
